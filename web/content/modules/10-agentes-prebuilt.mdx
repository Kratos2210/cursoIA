<Box kind="def" label="◈ Definición · Agente">

Un **agente** es un LLM metido en un **bucle** con acceso a herramientas, donde *el modelo decide cuándo parar*. Esa última parte es la definición entera: en una cadena, tú fijas cuántos pasos hay; en un agente, el modelo sigue pidiendo herramientas hasta que considera que ya puede responder.

Por eso un agente no es "una cadena más larga". Una cadena es una línea recta y su longitud se conoce antes de ejecutarla. Un agente es un ciclo cuya longitud **se descubre en tiempo de ejecución** — y por eso necesita un límite de iteraciones, un presupuesto y observabilidad.

<DefList>
  <Term>ReAct</Term>
  <Def>El patrón que sigue (*Reason + Act*): razona qué hacer, actúa llamando a una herramienta, observa el resultado, vuelve a razonar. Es el ciclo A→D del Módulo 08, repetido.</Def>
  <Term>create_react_agent</Term>
  <Def>La versión "ya hecha" de LangGraph: le pasas modelo + herramientas + memoria y te devuelve el agente con el ciclo montado. En el Módulo 13 lo abrimos por dentro.</Def>
  <Term>checkpointer</Term>
  <Def>Dónde se guarda el estado entre turnos. Con uno en memoria basta para probar; en producción va a Sqlite o Postgres para sobrevivir a un reinicio.</Def>
</DefList>

</Box>

<Flow>
  <Step n="1" title="Pregunta">Entra al agente con la memoria del hilo.</Step>
  <Step n="2" title="El modelo piensa">¿Me basta lo que sé o necesito una tool?</Step>
  <Step n="3" title="Actúa">LangGraph ejecuta la tool que pidió.</Step>
  <Step n="4" title="Observa">El resultado entra al historial…</Step>
  <Step n="2 otra vez" title="Vuelve a pensar">Repite hasta que no pida más tools.</Step>
  <Step n="fin" title="Responde">Redacta con los datos reales.</Step>
</Flow>

La flecha `↺` es todo el asunto: el paso 4 no termina la ejecución, la *devuelve* al paso 2. Un agente no es una cadena más larga, es una cadena **que se muerde la cola** hasta que el modelo deja de pedir herramientas.

<Box kind="analogy" label="◆ Analogía (de tu agent.py)">

Una **cadena** es una línea de ensamblaje (sin libertad). Un **router** es un recepcionista (te manda a una puerta y termina). Un **agente** es un empleado con cinturón y *autonomía*: piensa ➡ actúa ➡ observa ➡ responde, en ciclo.

</Box>

```python title="funcionaconver_v3_streaming.py · agente con memoria"
from langgraph.prebuilt import create_react_agent
from langgraph.checkpoint.memory import MemorySaver

memoria = MemorySaver()   # recuerda la charla (indexada por thread_id)

agente = create_react_agent(
    llm,
    tools=[calculadora_descuentos],
    checkpointer=memoria,
    prompt="Eres un asesor de ventas claro y amable.",
)

config = {"configurable": {"thread_id": "cliente_001"}}   # id de conversación
r = agente.invoke({"messages": [("user", "¿Cuánto pago por 3500 con 18% off?")]}, config)
print(r["messages"][-1].content)
```

```text title="▸ deberías ver (algo así)"
Con el 18% de descuento, pagarías 2870 soles. ¿Te ayudo con algo más?
```

Mucho más corto que el Módulo 08: LangGraph une cerebro + herramientas + memoria y corre el ciclo A→D solo. El `prompt=` da personalidad; el `thread_id` separa usuarios.

<Box kind="analogy" label="◆ Novedad LangChain 1.x · el camino recomendado">

En LangChain 1.x el estándar recomendado es `from langchain.agents import create_agent` (misma idea, API más limpia, soporta "middleware"). El curso usa `create_react_agent` de `langgraph.prebuilt` porque es el que ya tenías y **sigue funcionando** — son primos —, pero al usarlo verás un aviso de *deprecation* (`LangGraphDeprecatedSinceV10`): la función se mudó a `langchain.agents.create_agent`. Migrar es cambiar el import y añadir el paquete —`uv add langchain`—; todo lo demás de este módulo queda igual.

### Streaming token a token

```python title="streaming en un agente"
from langchain_core.messages import AIMessageChunk

for chunk, meta in agente.stream(
    {"messages": [("user", "Dame 3 tips de ventas.")]}, config,
    stream_mode="messages",
):
    if isinstance(chunk, AIMessageChunk) and chunk.content:
        print(chunk.content, end="", flush=True)
```

```text title="▸ deberías ver (va apareciendo token a token, no de golpe)"
1) Escucha antes de vender: pregunta qué necesita el cliente.
2) Muestra el beneficio, no la característica.
3) Cierra con una acción concreta: "¿lo agendamos?".
```

<Box kind="warn" label="▲ Cada vuelta del agente cuesta tokens">

Un agente **no responde en una sola llamada**: puede iterar varias veces por pregunta (pensar → pedir tool → observar → volver a pensar). Cada vuelta es **una llamada más al modelo**, y cada llamada son tokens que se cobran. Un agente que se "engancha" pidiendo herramientas puede multiplicar el coste de una consulta sin que te des cuenta. Vigila el gasto (Módulo 16) y pon un **límite de iteraciones** (`recursion_limit` en la config) para que un ciclo que se descontrola no se te lleve la cuota entera.

</Box>

<Avoid label="⛔ Cuándo NO usar un agente (usa una cadena)">

- **Cuando el flujo es predecible.** Si siempre haces los mismos pasos en el mismo orden, una cadena ([m02](/modulo/02-prompts-lcel)) o un router ([m08](/modulo/08-routing)) hace lo mismo más barato, más rápido y —lo importante— testeable de punta a punta.
- **Cuando el coste o la latencia importan.** Un agente puede dar varias vueltas por consulta; una cadena da una sola llamada. No pagues la autonomía si no la necesitas.
- **Cuando necesitas resultados reproducibles.** La longitud del ciclo de un agente se descubre en ejecución: eso es potencia, pero también imprevisibilidad. Para un paso que debe salir igual siempre, no uses un agente.

</Avoid>

<Box kind="def" label="◈ Más allá de ReAct: Plan-and-Execute y Reflexion">

ReAct decide **un paso a la vez**: pensar → actuar → mirar → repetir. Para muchas tareas basta, pero hay otras dos arquitecturas canónicas que conviene reconocer por nombre. **Plan-and-Execute** (también verás *Plan-and-Solve*): el agente primero escribe el **plan completo** ("1. buscar X, 2. cruzar con Y, 3. redactar") y luego lo ejecuta paso a paso, replanificando solo si algo falla. Gana cuando la tarea es **multi-paso con dependencias** — con ReAct puro, el agente puede perderse a mitad de camino porque nunca miró el problema entero; además los pasos planificados pueden usar un modelo más barato que el planificador. **Reflexion**: el agente genera, un **crítico** (él mismo u otro modelo) señala qué está mal, y reintenta con esa crítica en el contexto. Gana cuando lo que importa es la **calidad iterativa** de una salida (código que debe pasar tests, un informe con requisitos). Ninguna necesita otro framework: ambas se arman con el `StateGraph` del [m13](/modulo/13-langgraph-a-fondo) — Plan-and-Execute es un nodo planificador + un bucle de ejecución; Reflexion es exactamente el patrón generar→evaluar→reintentar del Paso 1 del m13. La elección es por caso de uso, no por moda: paso a paso exploratorio → ReAct; multi-paso con dependencias → Plan-and-Execute; calidad con criterio verificable → Reflexion.

</Box>

```python title="solución (es tu funcionaconver_v3_streaming.py)"
@tool
def consultar_disponibilidad(fecha: str) -> str:
    """Consulta horarios libres para una fecha. Úsala cuando el
    usuario PREGUNTA por disponibilidad, sin confirmar todavía."""
    return f"El {fecha} hay turnos a las 10:00 y 15:30"

@tool
def agendar_cita(fecha: str, hora: str, nombre: str) -> str:
    """Registra una cita. Úsala SOLO cuando el usuario CONFIRMA
    explícitamente que quiere agendar (dice 'sí', 'resérvame', etc.)."""
    return f"Cita agendada: {nombre}, {fecha} {hora}"

agente = create_react_agent(llm, tools=[consultar_disponibilidad, agendar_cita],
                            checkpointer=MemorySaver())
# "¿Tienes algo el viernes?"  -> consulta.  "Sí, resérvame a las 10" -> agenda.
```
