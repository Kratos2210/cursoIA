Hasta aquí todo fue texto → texto. Los modelos con **visión** (Gemini, GPT-5, Claude) reciben además **imágenes**: le mandas la foto de una factura y te la extrae, la captura de un error y te lo explica, un diagrama y te lo describe. Lo único nuevo es cómo se *arma* el mensaje: el contenido deja de ser un string y pasa a ser una **lista de bloques**.

<Box kind="def" label="◈ Definición · Contenido multimodal por bloques">

Un `HumanMessage` multimodal lleva en su `content` una **lista** donde cada elemento es un **bloque** con su `type`: uno de texto y uno de imagen. La imagen no viaja como bytes crudos (el JSON es texto) sino codificada en **base64** dentro de un `data:` URL.

<DefList>
  <Term>data: URL</Term>
  <Def>Una imagen incrustada como texto: `data:image/png;base64,iVBOR…`. El prefijo dice el tipo (MIME) y que lo que sigue es base64.</Def>
  <Term>base64</Term>
  <Def>Reescribe bytes binarios como texto ASCII para que quepan en el JSON de la petición. La stdlib de Python lo hace con `base64.b64encode`.</Def>
  <Term>bloque `image_url`</Term>
  <Def>El formato "chat completions" `{"type":"image_url","image_url":{"url": data_url}}`. Es el que `langchain-google-genai` traduce a la parte `inline_data` que la API de Gemini espera — y el mismo que hablan los proveedores compatibles con OpenAI.</Def>
  <Term>modelo con visión</Term>
  <Def>No todos ven. Gemini sí; el Qwen de texto en Groq, no. Si el proveedor no tiene visión, el bloque de imagen se ignora o da error.</Def>
</DefList>

</Box>

<Box kind="analogy" label="◆ Un sobre con dos hojas">

El mensaje multimodal es un **sobre** con dos hojas dentro: una con tu pregunta escrita y otra con la imagen pegada. El modelo abre el sobre y lee *ambas* como una sola entrada — "mira esto Y respóndeme aquello". El `data:` URL es la imagen "fotocopiada en texto" para que quepa en el sobre.

</Box>

### Paso 1 · La imagen como data: URL

```python title="22_multimodal.py · bytes → data: URL (stdlib base64)"
import base64

def imagen_a_data_url(datos, mime="image/png"):
    # PORQUÉ base64: el JSON de la petición es texto y no lleva bytes crudos.
    # base64 reescribe los bytes como ASCII; el prefijo dice qué tipo de imagen es.
    b64 = base64.b64encode(datos).decode("ascii")
    return f"data:{mime};base64,{b64}"
```

### Paso 2 · El mensaje con dos bloques

El `content` es una lista: bloque de texto y bloque de imagen. Este es el formato que **verificamos contra el paquete instalado**, no de memoria — el test confirma que `langchain-google-genai` lo traduce a una parte de imagen de Gemini.

```python title="22_multimodal.py · el mensaje multimodal"
from langchain_core.messages import HumanMessage

def mensaje_multimodal(texto, data_url):
    return HumanMessage(content=[
        {"type": "text",      "text": texto},
        {"type": "image_url", "image_url": {"url": data_url}},
    ])

# ...y se envía como cualquier otro mensaje (la llamada real necesita API key):
#   util.crear_llm().invoke([mensaje_multimodal(pregunta, data_url)])
```

<Box kind="warn" label="▲ Las imágenes cuestan tokens (y no todos ven)">

Una imagen se cobra como un buen puñado de tokens, y crece con su resolución. Manda fotos **redimensionadas**, no la captura de 4000×3000 del teléfono: pagas de más por detalle que el modelo no necesita. Y verifica que el proveedor **tenga visión** — mandarle una imagen a un modelo de solo texto es, en el mejor caso, dinero tirado.

</Box>

<Avoid label="⛔ Cuándo NO usar esto">

- No mandes imágenes **enormes sin redimensionar**: disparas tokens y coste por resolución que no aporta.
- No asumas visión en cualquier proveedor: el Qwen de texto en Groq (y muchos open weights) **no ven**. Cambiar de proveedor puede romper el multimodal aunque el resto del curso conmute solo.
- No uses multimodal cuando ya tienes el texto: si la factura llega como PDF con texto seleccionable, extraerlo y hacer RAG es más barato y exacto que "leer" la imagen.

</Avoid>

Segundo reto: añade un **tercer** bloque de imagen al mismo mensaje y pídele al modelo que compare las dos. El formato de bloques lo permite sin cambiar nada más.

**Criterio de aceptación:** `len(mensaje.content) == 3` y sus tipos son `['text', 'image_url', 'image_url']`. Con llave y un modelo con visión, la respuesta menciona algo que aparece **solo en la segunda** imagen — si te describe una sola, revisa que no estés pisando el bloque anterior en vez de añadirlo a la lista.

<Solution summary="Ver una solución">

```python title="solución · dos imágenes en el mismo mensaje"
from langchain_core.messages import HumanMessage

def mensaje_comparar(texto, data_urls):
    # El content es una LISTA: nada impide que lleve N bloques de imagen.
    # Se APILAN, no se sobrescriben — ese es todo el truco del formato por bloques.
    bloques = [{"type": "text", "text": texto}]
    for url in data_urls:
        bloques.append({"type": "image_url", "image_url": {"url": url}})
    return HumanMessage(content=bloques)

a = imagen_a_data_url(open("factura_a.png", "rb").read(), mime="image/png")
b = imagen_a_data_url(open("factura_b.png", "rb").read(), mime="image/png")
mensaje = mensaje_comparar("Compara ambas facturas: ¿qué campos difieren?", [a, b])

print(len(mensaje.content))                             # 3
print([bloque["type"] for bloque in mensaje.content])   # ['text', 'image_url', 'image_url']
# util.crear_llm().invoke([mensaje])  ← la llamada real, SOLO con un modelo con visión.
```

Dos avisos que el ejercicio hace evidentes. Uno: el coste **se duplica**, porque cada imagen paga sus tokens por resolución — comparar dos capturas de 4000×3000 sale caro por detalle que nadie mira. Dos: si el proveedor no ve, esto no falla ruidosamente; el bloque se ignora y el modelo te contesta algo plausible sobre nada. Verifica la capacidad antes, no después de leer la respuesta.

</Solution>

<Box kind="def" label="◈ Más allá de VER: oír, hablar y generar imágenes">

La imagen de entrada es solo una esquina del multimodal. El espectro completo tiene cuatro esquinas, y todas se arman con el mismo patrón de bloques que acabas de aprender:

<DefList>
  <Term>oír (audio → texto)</Term>
  <Def>El modelo transcribe o razona sobre un audio. Mismo patrón que la imagen, pero el bloque es `media` con su `mime_type` (verificado contra el paquete): `{"type":"media","mime_type":"audio/wav","data": "<base64>"}`. Lo tienes armado en **curso_ejemplos/22b_voz.py**.</Def>
  <Term>hablar (texto → audio, TTS)</Term>
  <Def>La síntesis de voz NO es un mensaje de chat: es una petición aparte cuya *respuesta son bytes de audio*, no texto. En `22b_voz.py` armas su payload (`input`, `voice`, `format`).</Def>
  <Term>generar imágenes (texto → imagen)</Term>
  <Def>Modelos texto→imagen (Imagen de Google, DALL·E, la generación de Gemini) devuelven una imagen, no texto. También es una API distinta de la de chat.</Def>
</DefList>

▲ Regla que se repite: el bloque `media`/`image_url` viaja igual, pero **el proveedor tiene que soportar esa modalidad** (Gemini oye y ve; un modelo de solo texto en Groq, no). Y audio/imagen pesan más que el texto: cuestan más y tardan más, así que mídelo ([c16](/concepto/16-observabilidad-y-costo)) antes de meterlo en el camino caliente.

</Box>

### Del batch al tiempo real

Todo lo anterior es **batch**: mandas el audio entero y esperas la respuesta entera. Un asistente de voz de verdad (un call-center con IA, un altavoz) no puede darse ese lujo — el usuario oiría silencio mientras habla y mientras el modelo piensa. La versión en **tiempo real** encadena tres flujos que corren *a la vez*, cada uno emitiendo por trozos:

<Flow>
  <Step n="1" title="STT streaming">El audio llega por trozos y se transcribe parcial, sin esperar a que termines de hablar.</Step>
  <Step n="2" title="LLM streaming">Con la transcripción, el modelo responde token a token (el mismo stream del [c10](/concepto/10-agentes-prebuilt)/[c25](/concepto/25-frontend-chat-sse)).</Step>
  <Step n="3" title="TTS por frases">En cuanto hay una frase completa, se sintetiza y se reproduce — no se espera al final.</Step>
</Flow>

La ganancia es la **latencia percibida**: la respuesta "empieza" casi al toque. En producción esto lo montan servicios especializados —**Deepgram** (STT), el streaming del propio LLM y **ElevenLabs**/**Cartesia** (TTS)— orquestados por algo como **LiveKit** o **Pipecat**. La *forma* del pipeline, en cambio, es simple y se puede simular sin red: `22b_voz.py` lo hace con un generador incremental (stdlib), inyectando el "modelo" por parámetro como en el resto del curso.

```python title="22b_voz.py · pipeline_voz_streaming (simulado, stdlib pura)"
def pipeline_voz_streaming(fragmentos_audio, responder):
    transcripcion = ""
    for trozo in fragmentos_audio:          # 1) STT: el audio llega a trozos…
        transcripcion += trozo
        yield ("parcial", transcripcion)    #    …y la transcripción crece
    yield ("final_stt", transcripcion)

    respuesta = ""
    for token in responder(transcripcion):  # 2) LLM: responde token a token
        respuesta += token
        yield ("token", token)

    for frase in _dividir_en_frases(respuesta):   # 3) TTS: una síntesis por frase completa
        yield ("audio", peticion_tts(frase, voz="verse"))
```

<Box kind="warn" label="▲ El tiempo real añade problemas que el batch no tiene">

Streaming de voz suena mágico, pero trae complicaciones nuevas: **barge-in** (el usuario interrumpe y hay que cortar el TTS a media frase), **detección de fin de turno** (¿terminó o solo hizo una pausa?) y el **presupuesto de latencia** —STT + LLM + TTS deben sumar menos de ~800 ms para que la charla se sienta natural. Para transcribir una nota de voz o narrar un texto, el **batch** de arriba basta y es mucho más simple. El tiempo real se gana cuando la conversación *fluida* es el producto.

</Box>

### 🏗 Proyecto guiado: un agente que VE (y opcionalmente habla)

Los conceptos anteriores te dieron piezas sueltas. Este proyecto las junta en algo que resuelve una tarea real: **el cliente manda una foto y el agente actúa**. Caso concreto —un asistente de reclamos— *"llegó rota la caja"* + foto → clasifica el daño, decide si procede reembolso y redacta la respuesta.

No hay archivo nuevo que copiar: **todo lo que necesitas ya está escrito y testeado**. Es trabajo de ensamblaje, que es exactamente lo que hace un AI Engineer.

<Box kind="practice" label="▸ Los cuatro pasos (y de dónde sale cada pieza)">

**1 · La entrada visual.** Usa `22_multimodal.py` tal cual: `imagen_a_data_url()` + el mensaje de dos bloques. El armado es offline; solo la llamada final necesita un modelo con visión.

**2 · El contrato de salida.** No dejes que responda un párrafo: exige un molde como el del [c09b](/concepto/09b-proyecto-utilidad-texto) — `{"dano": "leve|grave|ninguno", "procede_reembolso": bool, "respuesta": str}` — y **valídalo**. Aquí importa más que nunca: una decisión de reembolso la va a consumir otro sistema.

**3 · La acción.** Que el modelo no solo describa: dale herramientas ([c07](/concepto/07-herramientas)) y un agente que decida ([c10](/concepto/10-agentes-prebuilt)) — `registrar_reclamo(id, dano)` y `escalar_a_humano(motivo)`. La foto entra por el mensaje multimodal; la decisión sale por una tool.

**4 · La voz (opcional).** Si quieres que además escuche y conteste hablando, el pipeline está en `22b_voz.py` y su versión con servicios reales en el [c33](/concepto/33-agente-voz-realtime). Añádelo **al final**: primero que funcione con texto.

</Box>

<Box kind="def" label="◈ Criterios de 'hecho' (para que no te quedes en la demo bonita)">

- El sistema devuelve un **objeto validado**, no texto, y hay un test que lo comprueba con un doble (sin gastar cuota).
- Si la foto es ilegible o el modelo duda, **escala a un humano** en vez de inventar un veredicto — `requiere_humano` del c09b, `interrupt` del [c13](/concepto/13-langgraph-a-fondo).
- Registras **cuánto costó**: las imágenes se cobran caras (mira el aviso de tokens de arriba), así que mide antes de prometerle el precio a nadie.
- Una decisión de dinero **nunca** la cierra el modelo solo: revisa la caja de ética del [c23](/concepto/23-seguridad-red-teaming).

</Box>
