### Antes de empezar: prepara tu computadora

Si nunca programaste, este es tu punto de partida. Necesitas **tres cosas**: una terminal (ya la tienes), `uv` (lo instalas en un comando) y un editor para escribir tus archivos. Nada más.

#### 1 · La terminal (tu línea de comandos)

La **terminal** es una ventana donde escribes órdenes con el teclado en vez de hacer clic. Todos los comandos del curso se escriben ahí. Cómo abrirla:

- **Windows:** menú Inicio → escribe `PowerShell` → Enter.
- **macOS:** `Cmd + Espacio` → escribe `Terminal` → Enter.
- **Linux:** `Ctrl + Alt + T` (o busca "Terminal" en tus aplicaciones).

<Box kind="analogy" label="◆ Analogía">

La terminal es como enviarle notas escritas a tu computadora en lugar de señalarle cosas con el dedo. Al principio intimida porque no hay botones; pero cada comando de este curso está listo para **copiar y pegar**, así que no tienes que memorizar nada.

</Box>

#### 2 · Instala `uv`

`uv` es la herramienta que gestiona tu Python y tus librerías (y si te falta Python, `uv` lo instala solo). Pega en tu terminal el comando de tu sistema:

```python title="terminal · instalar uv"
# macOS o Linux:
curl -LsSf https://astral.sh/uv/install.sh | sh

# Windows (en PowerShell):
powershell -ExecutionPolicy ByPass -c "irm https://astral.sh/uv/install.ps1 | iex"
```

**Cierra la terminal y abre una nueva** (para que reconozca el nuevo programa) y comprueba que quedó instalado:

```bash title="terminal · verificar"
uv --version
```

```text title="▸ deberías ver (algo así)"
uv 0.9.x
```

Si en cambio dice `command not found: uv`, no abriste una terminal nueva o la instalación no terminó: repite el comando y vuelve a abrir la terminal.

#### 3 · Instala VS Code (tu editor)

Para escribir los archivos `.py` necesitas un editor de texto para programadores. El más usado es **Visual Studio Code**, gratis: descárgalo de [code.visualstudio.com](https://code.visualstudio.com) e instálalo como cualquier programa.

Para crear tu primer archivo: abre VS Code → menú *Archivo → Nuevo archivo* → menú *Archivo → Guardar como…* y ponle un nombre que termine en `.py` (por ejemplo `main.py`). Esa terminación es la que le dice a todo el mundo —y a `uv`— que dentro hay código Python. VS Code además trae su propia terminal integrada (menú *Terminal → Nueva terminal*), muy cómoda para no cambiar de ventana.

### Instalación (con `uv`)

```python title="terminal · setup.sh"
# Básico e intermedio
uv init mi-curso-ia && cd mi-curso-ia
uv add langchain langgraph python-dotenv pypdf

# Los dos clientes de modelo. langchain-openai no es "para OpenAI":
# es para CUALQUIER API que hable su dialecto — Groq, Ollama, Together…
uv add langchain-google-genai langchain-openai

# Avanzado (RAG pro + re-ranking)
uv add langchain-chroma langchain-text-splitters langchain-community rank-bm25

# Embeddings en tu máquina, sin cuota (opcional pero recomendado para el RAG)
uv add fastembed

# Producción (opcional)
uv add langchain-mcp-adapters langsmith

# Crea el .env con tu llave (NUNCA lo subas a git). Elige UNA:
echo "LLM_PROVIDER=google"                    >  .env   # opción A: Gemini
echo "GOOGLE_API_KEY=tu_llave_secreta"        >> .env

# echo "LLM_PROVIDER=groq"                    >  .env   # opción B: Groq
# echo "GROQ_API_KEY=gsk_tu_llave_secreta"    >> .env
# echo "EMBEDDINGS_PROVIDER=fastembed"        >> .env
```

Esos comandos hacen dos cosas distintas y conviene no confundirlas. `uv init` crea la carpeta del proyecto con un `pyproject.toml` **vacío de dependencias**. `uv add` es lo que las escribe ahí dentro *y* las instala. Si te saltas los `uv add`, tienes un proyecto perfectamente válido… que no sabe nada de LangChain.

<Box kind="warn" label="▲ El primer tropiezo de todo el mundo">

Al verificar la instalación verás esto:

```text title="▸ el síntoma"
$ uv run python -c "from dotenv import load_dotenv; print('listo')"
Using CPython 3.12.13
Creating virtual environment at: .venv
ModuleNotFoundError: No module named 'dotenv'
```

Parece que `uv` falló. No falló: hizo **exactamente** lo que le pediste. `uv run` nunca adivina qué necesitas — instala *solo* lo que declara el `pyproject.toml`. Si la lista `dependencies` está vacía, crea el entorno y no pone nada dentro. La línea `Creating virtual environment` es la pista: significa que ahí no había entorno, así que tampoco había nada instalado.

**La cura:** corre los `uv add` de arriba dentro de tu carpeta. Y si el error persiste, casi siempre es porque estás *parado en otro sitio*.

</Box>

<Box kind="analogy" label="◆ Dónde estás parado importa (la regla de oro de uv)">

`uv` elige el entorno buscando el `pyproject.toml` **más cercano hacia arriba** desde tu carpeta actual. Por eso el *mismo* comando funciona en una carpeta y falla en la de al lado, y por eso el curso te pide siempre `cd` antes de ejecutar. Cuando dudes, pregúntale a Python qué entorno está usando de verdad:

```bash title="diagnóstico · ¿qué .venv estoy usando?"
uv run python -c "import sys; print(sys.prefix)"
# .../mi-curso-ia/.venv   ← el tuyo, el que tiene tus uv add
# .../otro-proyecto/.venv ← estás en la carpeta equivocada: haz cd
```

En este curso hay **una sola carpeta de trabajo**: `mi-curso-ia/`. Ahí vives, ahí escribes tus archivos y ahí traes las librerías con `uv add`. Si un comando te falla, la primera pregunta no es "¿me faltó instalar algo?" sino **"¿estoy parado en `mi-curso-ia/`?"**. Nueve de cada diez veces, ese es el problema.

</Box>

### Consigue tu llave (paso a paso)

El modelo vive en los servidores de otra empresa; tu programa se identifica ante ellos con una **llave API**. Conseguirla es gratis y toma un minuto. **Tienes dos proveedores para elegir**, y el curso funciona igual con cualquiera de los dos.

<Box kind="analogy" label="◆ Cuál elegir (y por qué te vas a acabar pasando a Groq)">

**Gemini** es el camino por defecto del curso. **Groq** sirve `qwen/qwen3-32b` con un cupo gratuito *mucho* más generoso y respuestas bastante más rápidas.

La cuota gratuita de Gemini se agota en una tarde de práctica: verás un `429 RESOURCE_EXHAUSTED` y creerás que rompiste algo. No rompiste nada. Si vas a hacer los ejercicios del tirón, **empieza directamente en Groq**. Puedes tener las dos llaves y cambiar con una línea del `.env`.

</Box>

Para empezar, con Gemini o Groq te basta. Pero el conmutador entiende **más proveedores** — `openai`, `anthropic` (Claude), `openrouter` y `deepseek`, además de `ollama` en tu máquina — todos con la misma línea del `.env`. Cuándo y por qué elegir cada uno (pago vs. open weights, precios reales, dónde corre) lo ves en el [Módulo 18b · Elegir modelo y proveedor](/modulos/18b-elegir-modelo-y-proveedor).

#### Opción A · Gemini

1. Entra a [aistudio.google.com](https://aistudio.google.com).
2. Inicia sesión con tu cuenta de Google (la misma de Gmail sirve).

4. **Copia** la llave que aparece — empieza con `AIza…`.
5. Pégala en tu archivo `.env`, **reemplazando** el texto de relleno `tu_llave_secreta`.

El paso 5 es el que más confunde. El comando de instalación te dejó un `.env` con un texto de ejemplo; tú lo cambias por tu llave real:

```python title=".env · ANTES (lo que creó el comando)"

```

```python title=".env · DESPUÉS (con tu llave real, sin comillas ni espacios)"

GOOGLE_API_KEY=AIzaSyD-xxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
```

#### Opción B · Groq con `qwen/qwen3-32b`

1. Entra a [console.groq.com/keys](https://console.groq.com/keys).
2. Inicia sesión (con Google o GitHub, no hace falta tarjeta).
3. Haz clic en **"Create API Key"** y ponle cualquier nombre.
4. **Copia** la llave — empieza con `gsk_…`. Solo se muestra *una vez*.
5. Pégala en el `.env` y cambia el proveedor:

```python title=".env · con Groq"
LLM_PROVIDER=groq
GROQ_API_KEY=gsk_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
```

Eso es todo. Los ejemplos no cambian: todos llaman a `util.crear_llm()`, que lee el `.env` y construye el modelo del proveedor activo. Ninguno instancia un modelo a mano.

```python title="util.py · una clase para casi todo el mercado"
def crear_llm(temperature=0.0, modelo=None):
    activo = proveedor()                       # lo dice LLM_PROVIDER
    modelo = modelo or modelo_por_defecto(activo)

    if activo == "google":                     # Gemini habla su propio dialecto
        from langchain_google_genai import ChatGoogleGenerativeAI
        return ChatGoogleGenerativeAI(model=modelo, temperature=temperature)

    # Groq, Ollama, Together, OpenAI… todos hablan el dialecto de OpenAI.
    # Lo único que cambia entre ellos es la base_url.
    base_url, variable = _COMPATIBLES_OPENAI[activo]
    from langchain_openai import ChatOpenAI
    return ChatOpenAI(model=modelo, temperature=temperature,
                      base_url=base_url, api_key=os.getenv(variable))
```

<Box kind="analogy" label="◆ Por qué basta con eso">

No es que LangChain tenga un adaptador por proveedor: es que **el mercado convergió en un protocolo**. Groq, Ollama, Together y OpenAI hablan todos la misma API, así que una sola clase con otra `base_url` los cubre a los cuatro. Gemini no la habla, y por eso tiene su propia rama. También puedes usar `LLM_PROVIDER=ollama` para correr un modelo en tu propia máquina, sin llave y sin cuota.

</Box>

<Box kind="analogy" label="◆ Dos cosas que crear_llm() arregla por ti con Groq">

**1. El bloque `<think>`.** `qwen/qwen3-32b` es un **modelo de razonamiento**: antes de responder escribe su cadena de pensamiento, y Groq la devuelve *dentro* del contenido, envuelta en `<think>…</think>`. Sin tratarlo, todas las salidas del curso saldrían con ese ruido delante. `crear_llm()` envía `reasoning_format: "hidden"` y Groq lo descarta.

**2. La salida estructurada.** Por defecto, `with_structured_output()` pide `response_format: json_schema`. OpenAI lo soporta; **Groq solo en algunos modelos**, y `qwen3-32b` no está entre ellos: devolvía un `400` y el [Módulo 05](/modulos/05-salida-estructurada) se caía en seco. `crear_llm()` usa `method="function_calling"`, que consigue lo mismo declarando una herramienta con la forma del esquema.

Los dos parches son **específicos de Groq** y condicionales: `reasoning_format` solo se manda a modelos de razonamiento, porque a `llama-3.3-70b` le provoca un `400`. Esto es exactamente el trabajo invisible que ahorra una fábrica de modelos: si cada ejemplo instanciara el suyo, tendrías que recordar los dos parches diecinueve veces.

</Box>

#### El RAG no se salva: los embeddings y `fastembed`

Esto no lo vas a entender del todo hasta el [Módulo 11](/modulos/11-rag-profesional), y no pasa nada: **déjalo puesto en el `.env` y sigue**. Allí se explica qué es `fastembed` y por qué existe. Lo mínimo que necesitas saber ahora:

Además del modelo que *conversa*, el RAG usa un segundo modelo que convierte texto en números (**embeddings**) para poder buscar por significado. Ese segundo modelo **no** se cambia con `LLM_PROVIDER`, por dos razones:

1. **Groq no ofrece embeddings.** Ninguno. Si mueves el chat a Groq, el RAG se queda sin quien vectorice.
2. **Cambiar de modelo de embeddings invalida el índice entero.** No es como cambiar de modelo de chat, donde lo peor que pasa es que la respuesta suene distinta. Los vectores de `gemini-embedding-001` y los de otro modelo *viven en espacios distintos*: compararlos no da un resultado peor, da un resultado **sin sentido**. Hay que reindexar.

Por eso los embeddings tienen su propia variable. Y por eso existe una salida que no depende de ningún proveedor: **calcularlos en tu propia máquina** con `fastembed`.

```bash title="terminal · instalar los embeddings locales"
uv sync --extra emb     # trae fastembed (ONNX, sin PyTorch)
```

```python title=".env · chat en Groq, embeddings en tu portátil → cero cuota de Gemini"
LLM_PROVIDER=groq
GROQ_API_KEY=gsk_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx

EMBEDDINGS_PROVIDER=fastembed
```

Con esas cuatro líneas, `11_rag.py` vectoriza los fragmentos en tu máquina y solo el chat sale a internet. La primera ejecución descarga el modelo (~220 MB, multilingüe: el curso está en español); a partir de ahí funciona incluso sin conexión.

```text title="salida esperada · 11_rag.py con fastembed"
📄 Se crearon 7 fragmentos.

🙋 ¿Cuál es el horario de atención?
🤖 Atendemos de lunes a viernes, de 9:00 a 18:00.
```

<Box kind="warn" label="▲ Si ya habías indexado con otro modelo, reindexa">

En el curso no muerde: los ejemplos reconstruyen el índice en cada arranque, así que cambiar `EMBEDDINGS_PROVIDER` es inofensivo. En producción, donde el índice vive en una base de datos, cambiarlo **sin reindexar** deja un vector store que responde con basura convincente. Así lo resuelve [`proyecto_llmops/`](/llmops): los embeddings son locales *desde el principio*, precisamente para que ningún proveedor pueda obligarte a reindexar.

</Box>
