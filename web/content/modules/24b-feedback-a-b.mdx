Tienes dos redacciones del prompt del sistema: una larga (`agente_gobdata`) y una concisa (`agente_gobdata_conciso`). ¿Cuál responde mejor? Eso no lo decide quien escribió el prompt: lo decide el usuario. Para medirlo hacen falta dos piezas que encajan — **repartir** el tráfico entre las dos variantes y **recoger** el 👍/👎 agregado por variante. Sin las dos, no hay experimento.

<Box kind="def" label="◈ Definición · Bucketing pegajoso y feedback por variante">

<DefList>
  <Term>A/B pegajoso (sticky)</Term>
  <Def>El mismo `thread_id` cae **siempre** en la misma variante. La variante es una **función** del identificador, no un sorteo por request. Si alternara, el usuario vería A y B en la misma conversación y su voto no se podría atribuir a nada.</Def>
  <Term>Bucketing por hash</Term>
  <Def>`sha256(thread_id) % nº_variantes`. Es **reproducible** (cualquier worker calcula lo mismo sin coordinarse), **sin estado** (no guardas a quién le tocó qué) y **uniforme** (el hash reparte parejo).</Def>
  <Term>Feedback 👍/👎</Term>
  <Def>Un pulgar se pulsa; una nota de 1 a 5 se piensa. Se agrega por variante en una `tasa_aprobacion` (👍/total). Comparar esa tasa entre A y B es el resultado del experimento.</Def>
</DefList>

</Box>

<Box kind="analogy" label="◆ La cola del súper que no cambia de fila">

Imagina que al entrar te asignan una caja por tu número de socio, no al azar en cada compra. Vuelves mañana y te toca la misma caja: puedes comparar de verdad "¿la caja A atiende mejor que la B?" porque cada cliente vive una sola experiencia. Si te reasignaran caja a cada artículo, nadie sabría a qué caja agradecer o culpar. El **hash del `thread_id`** es ese "número de socio": pegajoso y sin que la caja tenga que recordarte.

</Box>

### Paso 1 · Bucketing determinista y pegajoso por hash

```python title="proyecto_llmops/prompts/experimentos.py · asignar_variante (stdlib hashlib)"
def asignar_variante(clave, variantes):
    # sha256(clave) es un entero de 256 bits repartido uniforme; su concepto
    # reparte parejo entre variantes. La MISMA clave -> SIEMPRE la misma variante.
    # ⭐ No se usa hash() de Python: está aleatorizado por proceso
    #    (PYTHONHASHSEED), así dos workers asignarían distinto al mismo usuario.
    digest = hashlib.sha256(clave.encode("utf-8")).hexdigest()
    return variantes[int(digest, 16) % len(variantes)]
```

### Paso 2 · El voto, agregado por variante

El feedback vive en **su propio endpoint**, no en `/metrics`: coste/latencia y satisfacción son ejes distintos, y así el `resumen()` de métricas no gana claves que sus tests no esperan.

```python title="proyecto_llmops/observability/feedback.py · resumen() agrega por variante"
def resumen(self):
    agregado = {}
    for voto in self.votos:
        casilla = agregado.setdefault(voto.variante,
            {"util": 0, "no_util": 0, "total": 0, "tasa_aprobacion": 0.0})
        casilla["util" if voto.util else "no_util"] += 1
        casilla["total"] += 1
    for casilla in agregado.values():             # 👍 / total: ordena A frente a B
        casilla["tasa_aprobacion"] = round(casilla["util"] / casilla["total"], 3)
    return agregado
```

```text title="▸ deberías ver al pedir GET /feedback (tras unos votos)"
{
  "agente_gobdata":         {"util": 8, "no_util": 4, "total": 12, "tasa_aprobacion": 0.667},
  "agente_gobdata_conciso": {"util": 9, "no_util": 2, "total": 11, "tasa_aprobacion": 0.818}
}
```

<Box kind="warn" label="▲ El evento fin anuncia la variante — sin romper nada">

El cambio es **aditivo**: el evento SSE `fin` de `/chat` gana una clave `"variante"` junto a `cache_hit` y `similitud`, que **siguen ahí**. Así el cliente sabe qué variante vio y puede devolverla en su voto. Los smoke tests existentes (`test_smoke_api.py`) no se tocaron y siguen en verde.

</Box>

<Avoid label="⛔ Cuándo NO fiarte del resultado">

- No declares ganadora una variante con **tres votos**: 3-0 puede ser azar. El ganador se decide con **significancia estadística**, no comparando dos fracciones pequeñas.
- No guardes el feedback solo **en memoria** en producción: se pierde al reiniciar y cada worker cuenta lo suyo. Va a una tabla o a Langfuse.
- No sortees la variante **por request**: sin pegajosidad, el experimento no mide nada.

</Avoid>

<Box kind="def" label="◈ ¿Cuántos votos bastan? · el test z de dos proporciones">

El Avoid de arriba dice "hace falta significancia". Aquí está, sin misterio. Comparas dos tasas de aprobación (`p_A`, `p_B`) y preguntas: *¿la diferencia es real o pudo salir por azar?* La herramienta estándar es el **test z de dos proporciones**.

<Formula>
z = (p_A − p_B) ÷ √( p·(1−p)·(1/n_A + 1/n_B) ) , con p = (👍_A + 👍_B) ÷ (n_A + n_B)
</Formula>

Regla de bolsillo: **|z| ≥ 1.96** ⇒ la diferencia es significativa al 95%. Y para *tener* con qué detectar una mejora de ~10 puntos necesitas del orden de **~100 votos por variante**, no tres.

```python title="significancia.py · z de dos proporciones (stdlib, ilustrativo)"
from math import sqrt

def z_dos_proporciones(util_a, n_a, util_b, n_b):
    """¿La diferencia entre dos tasas de aprobación es real o azar?
    |z| >= 1.96 -> significativa al 95%. Solo `math`, sin dependencias."""
    p_a, p_b = util_a / n_a, util_b / n_b
    p = (util_a + util_b) / (n_a + n_b)          # tasa combinada (hipótesis nula)
    se = sqrt(p * (1 - p) * (1/n_a + 1/n_b))     # error estándar de la diferencia
    return (p_a - p_b) / se if se else 0.0

print(round(z_dos_proporciones(8, 12, 9, 11), 2))      # -0.83  -> NO concluyente (pocos votos)
print(round(z_dos_proporciones(80, 120, 90, 110), 2))  # -2.61  -> SÍ: la concisa gana al 95%
```

Con los 12 y 11 votos del ejemplo de arriba, `|z|` no llega a 1.96: **empate estadístico**, aunque `0.818` "se vea" mejor que `0.667`. Multiplica los votos por 10 y la *misma* diferencia sí es significativa. Esa es toda la distancia entre una opinión con pasos y una decisión.

</Box>

**Segundo reto: audita el bucketing antes de fiarte de ningún resultado.** Asigna 1000 `thread_id` sintéticos, comprueba que el reparto es uniforme y que reasignar la misma clave da siempre lo mismo. Después calcula cuántos votos te faltarían para que tu diferencia actual fuera significativa.

**Criterio de aceptación:** el reparto queda a ±3 puntos del 50/50 con 1000 claves, la reasignación coincide en el **100%** de los ids, y sabes decir el `|z|` de tus votos de hoy y si pasa de 1.96. Un experimento cuyo repartidor no auditaste no mide el prompt: mide tu suerte.

<Solution summary="Ver una solución">

```python title="solución · auditar el repartidor antes de creerte el experimento"
from collections import Counter
from math import sqrt
from proyecto_llmops.prompts.experimentos import asignar_variante

VARIANTES = ["agente_gobdata", "agente_gobdata_conciso"]
claves = [f"thread-{i}" for i in range(1000)]

# 1) UNIFORMIDAD · sha256 % n reparte parejo, y tú no guardas estado de nadie.
print(Counter(asignar_variante(c, VARIANTES) for c in claves))      # ~500 / ~500

# 2) PEGAJOSIDAD · la MISMA clave, la MISMA variante — en cualquier worker y cualquier día.
assert all(asignar_variante(c, VARIANTES) == asignar_variante(c, VARIANTES) for c in claves)

# 3) ¿CUÁNTOS VOTOS FALTAN? Escala las mismas proporciones y mira cuándo |z| pasa 1.96.
def z(util_a, n_a, util_b, n_b):
    p_a, p_b = util_a / n_a, util_b / n_b
    p = (util_a + util_b) / (n_a + n_b)              # tasa combinada (hipótesis nula)
    se = sqrt(p * (1 - p) * (1 / n_a + 1 / n_b))
    return (p_a - p_b) / se if se else 0.0

for factor in (1, 3, 5, 10):
    print(factor, round(abs(z(8 * factor, 12 * factor, 9 * factor, 11 * factor)), 2))
# 1 -> 0.83 · 3 -> 1.43 · 5 -> 1.85 · 10 -> 2.61
```

Fíjate en lo que **no** cambia en ese último bucle: las tasas siguen siendo 0.667 y 0.818 en las cuatro filas. La diferencia entre variantes es idéntica; lo único que crece es la **evidencia**. Por eso "B se ve mejor" no es un resultado — con 12 y 11 votos es exactamente el mismo dato que con 120 y 110, salvo que uno permite decidir y el otro no.

Y el paso 2 no es paranoia: si alguien "optimizara" `asignar_variante` cambiando `hashlib.sha256` por el `hash()` de Python, este assert seguiría pasando dentro de un proceso y **fallaría silenciosamente entre workers** — que es justo donde vive tu producción.
