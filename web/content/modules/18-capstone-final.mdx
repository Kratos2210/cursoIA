Trabajas en Gobierno de Datos y Cumplimiento de una organización financiera. Construyes un asistente que **responde dudas sobre normativa**, **evalúa reglas de calidad de datos** y **registra hallazgos** — con aprobación humana antes de marcar un incumplimiento.

<Box kind="def" label="◈ Definición · Capstone (proyecto integrador)">

Un **capstone** o **proyecto integrador** es el trabajo final que **junta en un solo sistema** todo lo que aprendiste por partes. No introduce conceptos nuevos: demuestra que sabes *combinarlos* bajo las restricciones de un caso real (aquí, una financiera regulada). Si algo del curso no encajaba, aquí encaja.

<DefList>
  <Term>audit trail (rastro de auditoría)</Term>
  <Def>El registro escrito, en orden y **append-only** (solo se añade, nunca se borra), de cada decisión que toma el sistema y cada herramienta que ejecuta. En banca y salud no es opcional: el regulador puede exigir demostrar *qué* se decidió, *cuándo* y *con qué base*. Este proyecto lo escribe en `hallazgos_auditoria.log`.</Def>
</DefList>

</Box>

### Pieza 1 · RAG como herramienta

```python title="capstone · buscar_normativa"
from langchain_core.tools import tool

@tool
def buscar_normativa(pregunta: str) -> str:
    """Busca en la normativa y reportes regulatorios indexados.
    Úsala para responder dudas sobre reglas de calidad de datos."""
    docs = retriever_pro.invoke(pregunta)   # retriever con re-ranking (Concepto 12)
    return "\n\n".join(d.page_content for d in docs)
```

### Pieza 2 · Evaluación con salida estructurada

```python title="capstone · HallazgoCalidad"
from pydantic import BaseModel, Field

class HallazgoCalidad(BaseModel):
    """Resultado de evaluar una regla de calidad de datos."""
    regla: str
    cumple: bool
    severidad: str = Field(description="alta | media | baja")
    justificacion: str = Field(description="por qué cumple o no")

evaluador = llm.with_structured_output(HallazgoCalidad)
```

### Checklist por fases

1. **Fase 1 — Ingesta**: carga PDFs, trocéalos con `RecursiveCharacterTextSplitter` e indéxalos en Chroma persistente.
2. **Fase 2 — Recuperación de calidad**: añade re-ranking (cross-encoder) y, si hay códigos exactos, búsqueda híbrida.
3. **Fase 3 — Herramientas**: envuelve el RAG como `buscar_normativa`, crea `evaluar_regla_calidad` (Pydantic) y `registrar_hallazgo`.
4. **Fase 4 — Orquestación**: monta un `StateGraph` con memoria por analista y un nodo `interrupt` para aprobar incumplimientos.
5. **Fase 5 — Escala y resiliencia**: `with_fallbacks` entre modelos y `abatch` para evaluar muchas reglas en paralelo.
6. **Fase 6 — Producción**: separa servicios (Concepto 15b), registra un **audit trail** de cada decisión, corre tests de evaluación, activa LangSmith + Arize y escribe los ADR (Concepto 17).

### Mini-ADR de ejemplo

| Decisión | Por qué |
| --- | --- |
| Chroma persistente (no en memoria) | Volumen bajo/medio; evita re-indexar y no añade costo de servicio externo. |
| Re-ranker cross-encoder | La normativa tiene fragmentos muy parecidos; la precisión del contexto es crítica para no dar respuestas erróneas de cumplimiento. |
| Human-in-the-loop antes de marcar incumplimiento | Una marca errónea tiene consecuencias regulatorias; exige validación humana. |
| StateGraph en vez de prebuilt | Necesitamos el nodo de aprobación y ramas propias, no cabe en `create_agent`. |
| Audit trail de cada decisión | En una financiera, toda evaluación debe ser trazable y auditable ante el regulador. |

<Box kind="warn" label="▲ Errores comunes">

**429 RESOURCE_EXHAUSTED**: cupo agotado → fallbacks/reintentos o modelo de pago. **Respuestas inventadas**: falta la regla "responde solo con el contexto" en el prompt del RAG. **Tool equivocada**: mejora los docstrings.

<Solution summary="Ver una solución">

**Caso elegido:** asistente de **siniestros de seguros**. Responde dudas sobre las coberturas de una póliza, evalúa si un siniestro reportado encaja en ellas y registra el dictamen.

| Decisión | Por qué |
| --- | --- |
| Chroma persistente sobre el clausulado de cada producto | El corpus es acotado y cambia por versión de póliza, no a diario: no justifica una DB vectorial gestionada (c24). |
| Re-ranker cross-encoder | Las cláusulas de exclusión se parecen muchísimo entre sí; recuperar la del producto equivocado produce un dictamen erróneo. |
| `interrupt` **antes de emitir un rechazo de cobertura** | Un rechazo tiene efecto legal sobre el asegurado y es reclamable. El modelo *propone* el dictamen; lo firma un perito. Aprobar un pago menor sí puede ir automático. |
| Audit trail con **qué cláusula sostuvo el dictamen** | No basta con "se rechazó": ante el regulador o una demanda hay que poder señalar el artículo exacto, la versión del clausulado y quién aprobó. |
| `construir_agente(modelo, evaluador, retriever)` | El evaluador de cobertura es la lógica de negocio: con un doble que recita un dictamen fijo, los tests cubren el camino "rechazo → interrupt → registro" sin gastar cuota ni tocar una póliza real. |

**Las 6 fases, qué cambia:** *(1) Ingesta* — no son PDFs sueltos: cada clausulado se indexa **con su versión** en la metadata, porque un siniestro se juzga con la póliza vigente en la fecha del hecho. *(2) Recuperación* — el híbrido pesa más que en el caso financiero: los códigos de producto son literales y el vectorial solo no los caza (c12). *(3) Herramientas* — `buscar_clausula`, `evaluar_cobertura` (Pydantic: `cubierto`, `articulo`, `monto_estimado`, `justificacion`) y `registrar_dictamen`. *(4) Orquestación* — el `thread_id` es el **número de siniestro**, no el analista: el hilo sigue al caso aunque cambie el perito. *(5) Escala* — `abatch` para revisar la cola nocturna de siniestros simples; los complejos van por el camino con humano. *(6) Producción* — el audit trail es aquí el entregable principal, no un extra: es lo que se enseña en una auditoría.

</Solution>
