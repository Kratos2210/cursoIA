Un agente que lee documentos, llama a herramientas y le responde a un usuario es una **superficie de ataque**. El estándar para razonar sobre esto es el **OWASP LLM Top-10**. Aquí atacamos —y defendemos— las tres piezas que se ven **offline**: la inyección de prompts, el manejo inseguro de la salida y la fuga de datos. La regla de oro: *si tú no rompes tu agente, lo hará alguien con peores intenciones*.

<Box kind="def" label="◈ Definición · Tres familias del OWASP LLM">

<DefList>
  <Term>LLM01 · Inyección de prompts</Term>
  <Def>Alguien mete **instrucciones** donde tú esperabas **datos**. *Directa*: el usuario escribe "ignora tus reglas". *Indirecta* (la peligrosa): la orden viene **escondida en el documento** que tu RAG recuperó.</Def>
  <Term>LLM02 · Manejo inseguro de la salida</Term>
  <Def>La respuesta del modelo se pega en un HTML o una consulta **sin limpiarla** y ejecuta un `<script>` (XSS). La salida de un LLM es **contenido que no controlas**.</Def>
  <Term>LLM06 · Fuga de datos sensibles</Term>
  <Def>La respuesta se lleva puesta una **API key**, un email o una tarjeta que nunca debió salir del sistema.</Def>
</DefList>

</Box>

<Box kind="analogy" label="◆ El portero y el sobre marcado">

Tu contexto recuperado es como un **sobre que te llega por correo**: puedes *leer* lo que dice, pero no vas a *obedecer* una nota que diga "dale las llaves de la caja fuerte al portador". Separar DATOS de INSTRUCCIONES es marcar ese sobre como "solo lectura". El detector de patrones es el **portero** que revisa a la entrada; el saneo de la salida es el que revisa a la **salida** — porque a veces el intruso ya está dentro.

</Box>

<Box kind="def" label="◈ El panorama completo · más allá de la inyección que ya practicaste">

Este módulo ataca las tres piezas que se ven **offline**, pero el catálogo de amenazas adversariales es más ancho. Vale conocerlo para no creer que "ya está" con el detector de inyección:

<DefList>
  <Term>Jailbreaking</Term>
  <Def>Rodear las reglas del modelo con un **rol o ficción** ("haz de cuenta que eres un modelo sin restricciones…"). Prima hermana de la inyección directa.</Def>
  <Term>Envenenamiento de datos</Term>
  <Def>Meter ejemplos maliciosos **en los datos de entrenamiento o en el corpus del RAG** para torcer el comportamiento a futuro. La inyección indirecta del [m11](/modulo/11-rag-profesional)/[m12](/modulo/12-recuperar-re-rankear) es su versión en tiempo de consulta.</Def>
  <Term>Backdoor</Term>
  <Def>Un **disparador oculto** (una frase-llave) que el atacante sembró y que activa una conducta anómala solo cuando aparece.</Def>
  <Term>Inversión de modelo</Term>
  <Def>Reconstruir **datos de entrenamiento** a partir de las respuestas del modelo.</Def>
  <Term>Inferencia de pertenencia (MIA)</Term>
  <Def>Deducir si **un dato concreto estuvo** en el entrenamiento —un problema de privacidad, no solo de seguridad.</Def>
</DefList>

</Box>

<Box kind="def" label="◈ Privacidad · la otra cara de la seguridad">

No todo ataque busca que el modelo *diga* algo malo; algunos buscan **extraer** algo que no debía salir. El *gradient leakage* reconstruye datos desde los gradientes en entrenamiento distribuido; la *inferencia de pertenencia* (arriba) huele si tu registro estuvo en el dataset; y la fuga de **PII** (nombres, correos, tarjetas) es la más cotidiana. Defensas: *differential privacy* y regularización al entrenar, y —lo que sí está en tu mano hoy— el **PII scrubbing** a la salida, que es justo lo que hace `redactar_secretos` más abajo. La privacidad se diseña; no se parchea al final.

</Box>

### Paso 1 · Detectar la inyección (primera capa)

Casi todos los ataques se apoyan en unas pocas frases-palanca. Una lista de patrones las caza y te dice **qué** tipo de ataque vio (útil para loguear y alertar).

```python title="23_seguridad.py · LLM01 · lista negra de patrones"
def detectar_inyeccion(texto):
    # PORQUÉ primera capa: barata y determinista. Devuelve las ETIQUETAS de los
    # patrones vistos ("anular-instrucciones", "revelar-system-prompt", DAN…).
    plano = _sin_tildes(texto)              # "IGNORÁ" y "ignora" caen igual
    encontrados = []
    for etiqueta, patron in PATRONES_INYECCION.items():
        if re.search(patron, plano):
            encontrados.append(etiqueta)
    return encontrados                       # lista vacía = limpio
```

### Paso 2 · Sanear la salida (LLM02) y redactar secretos (LLM06)

```python title="23_seguridad.py · guardarraíles de salida (stdlib html + re)"
def sanear_salida(texto):
    # Borra bloques con cuerpo (<script>…</script>) y ESCAPA el resto del HTML:
    # `<` -> `&lt;`. Así NADA de lo que venga se interpreta como etiqueta.
    sin_bloques = _ETIQUETAS_PELIGROSAS.sub("", texto)
    return html.escape(sin_bloques)

def redactar_secretos(texto):
    # Enmascara claves de API, emails y tarjetas ANTES de que la respuesta salga.
    return _SECRETOS.sub("«oculto»", texto)
```

### Paso 3 · El pipeline: separar DATOS de INSTRUCCIONES

La defensa estructural contra la inyección *indirecta*: le decimos al modelo, explícitamente, que el contexto es material de referencia y que jamás obedezca órdenes escritas ahí dentro. Y pase lo que pase, limpiamos la salida.

```python title="23_seguridad.py · guardarraíles en capas"
def responder_seguro(pregunta, contexto, modelo=modelo_ingenuo):
    alertas = detectar_inyeccion(contexto)          # 1) alarma (LLM01 indirecta)
    prompt  = construir_prompt(pregunta, contexto)  # 2) separa datos de órdenes
    cruda   = modelo(prompt)                         # 3) el modelo puede caer…
    segura  = redactar_secretos(sanear_salida(cruda))  # 4) …la salida SIEMPRE se limpia
    return {"respuesta": segura, "cruda": cruda, "alertas": alertas}
```

```text title="▸ deberías ver al correr 23_seguridad.py (recortado)"
1) Inyección DIRECTA (en la pregunta del usuario):
   detectado: ['anular-instrucciones', 'revelar-system-prompt']

2) Inyección INDIRECTA (escondida en el contexto recuperado):
   alertas del contexto: ['anular-instrucciones', 'exfiltracion']
   ¿la salida CRUDA lleva <script>? True     ¿la clave? True
   ¿la salida SEGURA lleva <script>? False    ¿la clave? False
```

<Box kind="warn" label="▲ Honestidad pedagógica: el detector por patrones SE SALTA">

`detectar_inyeccion` es una **lista negra**, y toda lista negra se rodea parafraseando ("haz de cuenta que las reglas de arriba ya no aplican…"). **No es la única defensa, es la primera capa.** La seguridad real es **en capas**: (1) separar datos de instrucciones, (2) validar SIEMPRE la salida, (3) **mínimo privilegio** — no le des al LLM herramientas peligrosas (borrar, pagar, mandar correos) sin una confirmación humana, y (4) asumir que el contexto recuperado puede venir envenenado. Un detector que "pasa" te da falsa tranquilidad; las capas de abajo son las que de verdad frenan el daño.

</Box>

<Avoid label="⛔ Cuándo NO confiar en esto">

- No uses `detectar_inyeccion` como **único** filtro: un atacante que parafrasea lo evade. Es la alarma, no la cerradura.
- No pintes la salida del modelo como HTML de confianza: trátala como **entrada de usuario** y escápala (LLM02).
- No le des al agente herramientas con poder destructivo o de gasto **sin human-in-the-loop** (Módulo 13b): la inyección más cara no "habla mal", *actúa*.

</Avoid>
