El primer caso del curso (el capstone del [c18](/concepto/18-capstone-final)) fue gobierno de datos en una financiera: documentos, normativa, auditoría. Este segundo caso es el mundo opuesto y es **real y verificable**: **Sifrah**, cadena peruana de bisutería y accesorios de moda para mujer, con más de **90 tiendas** a nivel nacional (Lima, Arequipa, Trujillo, Cusco, Piura…) y e-commerce sobre Shopify. Y aquí el regalo para quien aprende: su catálogo es **público** — como toda tienda Shopify, `sifrah.com/products.json` devuelve los productos con título, tags, precio, precio de oferta y disponibilidad. Datos reales, de una empresa real, sin pedir permiso ni llave. *(Caso de estudio pedagógico sobre datos públicos; el curso no está afiliado a la marca.)*

<Box kind="def" label="◈ Cinco soluciones sobre la mesa (y por qué ganó la primera)">

Un consultor no llega con "un chatbot": llega con un **menú de casos**, cada uno con su dato y su retorno — el método que produce ese menú es el discovery del [c35](/concepto/35-discovery-de-procesos). Para una cadena así, los cinco naturales:

1. **Asistente de compras conversacional** — "quiero aretes dorados por menos de S/25" → recomendación con precios reales del catálogo. Dato: el catálogo (público). Retorno: conversión.
2. **Búsqueda semántica en el e-commerce** — que "aros" encuentre "aretes" (multi-query del c20 + embeddings del c11). Dato: el mismo catálogo. Retorno: menos búsquedas vacías.
3. **Copiloto interno de tienda** — las vendedoras de 90+ tiendas consultando stock, precios y promos (2x1, 3x2) por WhatsApp. Dato: inventario interno. Retorno: horas de piso.
4. **Enriquecimiento automático del catálogo** — miles de SKUs importados por temporada; salida estructurada (c05) + visión (c22) para generar categorías, materiales y descripciones. Retorno: tiempo de catalogación.
5. **Clasificación de reclamos y postventa** — sentimiento + enrutamiento de quejas (cambios, delivery) antes de que escalen. Retorno: riesgo reputacional.

**Ganó la 1** por tres criterios que valen para cualquier proyecto (la matriz del [c35](/concepto/35-discovery-de-procesos), formalizada): el **dato ya existe y es accesible** (no hay que esperar a un área de sistemas), el caso **integra lo que ya sabes** (estructurada + RAG + guardrails + evals: c05·c11·c16c·c23), y el **riesgo de equivocarse es medible** (un precio inventado se detecta con un guardrail determinista). Las otras cuatro son variaciones del mismo esqueleto — la 2 es el paso 3 de este concepto con embeddings, la 3 es este mismo pipeline sobre otra fuente.

</Box>

<Box kind="analogy" label="◆ La vendedora estrella">

La mejor vendedora de una tienda hace tres cosas: **entiende** lo que la clienta quiere aunque lo diga a su manera ("algo para el pelo, baratito"), **solo ofrece lo que hay** —jamás inventa un precio ni promete stock que no vio—, y si no hay, **lo dice** y propone alternativa. El asistente de este concepto es exactamente eso: el LLM pone la comprensión y la redacción; el catálogo pone los hechos. Cuando un chatbot de retail falla, es porque invirtió los papeles.

</Box>

### El dato real (y su primera trampa)

Así se ve un producto del endpoint real — precio como *string*, la promo escondida en `compare_at_price`, y una sorpresa:

```json title="sifrah.com/products.json · un producto real (recortado)"
{"title": "Mochila 2 en 1 Travel Fucsia",
 "product_type": "Joyería",              ← ¡la MOCHILA dice "Joyería"!
 "tags": ["Mochila", "Promocional", "Colección Julio 2026"],
 "variants": [{"price": "12.90",         ← string, no número
               "compare_at_price": "39.90",   ← si es mayor: está en promo
               "available": true}]}
```

De los 250 productos de la primera página, **249 dicen `product_type: "Joyería"`** — mochilas, cepillos y espejos incluidos. La categoría de verdad vive en el título y los tags, y hay que **derivarla**. Esta es la lección que ningún tutorial con datos limpios te da: *el dato real llega sucio, y el ETL no es burocracia — es la diferencia entre un asistente y un bochorno*.

### La arquitectura: cómo fluye una petición

El pipeline de siete pasos de arriba es la *narrativa*. Vista como **arquitectura**, se lee en tres capas: el camino de una petición en tiempo real, la capa de datos que le da los hechos, y las capas de producción que la hacen servible y medible. Las tres son el [proyecto_retail/](/concepto/29-caso-real-2-retail#c29-proyecto) —el build organizado del caso, al estilo del [proyecto_llmops](/recurso/llmops)—.

### Paso 2 · ETL: la categoría no se confía, se deriva

```python title="29_caso_retail.py · normalizar_producto (el dato real nunca llega listo)"
def normalizar_producto(crudo):
    variante = crudo["variants"][0]
    precio = float(variante["price"])              # "12.90" → 12.9
    antes = variante.get("compare_at_price")
    texto = _sin_tildes(f"{crudo['title']} {' '.join(crudo['tags'])}".lower())

    categoria = "otros"                            # product_type MIENTE:
    for nombre, claves in _CATEGORIAS:             # se deriva de título+tags
        if any(clave in texto for clave in claves):
            categoria = nombre
            break

    return {"sku": variante["sku"], "titulo": crudo["title"],
            "categoria": categoria, "precio": precio,
            "en_promo": antes is not None and float(antes) > precio,
            "disponible": bool(variante["available"]), "texto": texto}
```

### Paso 3 · Entender la petición: de la frase a filtros tipados

"Quiero aretes dorados por menos de 25 soles" son **tres filtros** disfrazados de frase: categoría, color, presupuesto. En el ejemplo se extraen con reglas (deterministas → testeables byte a byte); en producción este paso ES el [c05](/concepto/05-salida-estructurada): `llm.with_structured_output(FiltrosCompra)` con un molde Pydantic, que entiende "algo lindo pa' mi flaca, unos 30 lucas" mucho mejor que un regex. La **interfaz no cambia** (petición → filtros tipados): por eso puedes subir de nivel sin tocar el resto del pipeline.

### Paso 4 · Buscar: el presupuesto es un WHERE, no una preferencia

```python title="29_caso_retail.py · buscar_productos (filtros duros primero, ranking después)"
def buscar_productos(filtros, catalogo, k=3):
    # PORQUÉ dos fases: un producto de S/39.90 ante un tope de S/25 no es
    # "menos relevante" — es INVÁLIDO. Eso lo resuelve un filtro (el WHERE
    # del c24), jamás el ranking.
    candidatos = [p for p in catalogo if p["disponible"]]
    if filtros.get("presupuesto") is not None:
        candidatos = [p for p in candidatos if p["precio"] <= filtros["presupuesto"]]
    if filtros.get("categoria"):
        candidatos = [p for p in candidatos if p["categoria"] == filtros["categoria"]]

    def afinidad(p):   # SOLO entre los válidos se ordena por afinidad
        con_color = filtros.get("color") and filtros["color"] in p["texto"]
        return (1 if con_color else 0, -p["precio"])

    return sorted(candidatos, key=afinidad, reverse=True)[:k]
    # Y la regla del c20: si nada cumple → LISTA VACÍA. "No tengo" es una
    # respuesta válida; un sustituto fuera de presupuesto no lo es.
```

### Paso 5 · Grounding: el guardrail que salva del precio inventado

```python title="29_caso_retail.py · respuesta_es_fiel (anti-alucinación de precios)"
def respuesta_es_fiel(texto, productos):
    # ¿Cada S/xx.xx citado existe en los productos recuperados? Mismo espíritu
    # que el detector del c28 (desconfiar de lo no sostenido), pero AQUÍ la
    # fuente de verdad existe —el catálogo—, así que se verifica contra ella.
    permitidos = {round(p["precio"], 2) for p in productos}
    return all(round(precio, 2) in permitidos for precio in precios_citados(texto))
```

Anécdota de guerra (real, de este mismo concepto): la primera versión de la respuesta **ecoaba la petición** — "Para «…hasta S/80» te recomiendo…" — y el guardrail saltó: ese S/80 del usuario no es un precio del catálogo. La cura fue no re-inyectar el texto del usuario en la salida, la misma higiene que el [c23](/concepto/23-seguridad-red-teaming) pide contra la inyección. Un guardrail que te muerde a ti antes que al cliente está haciendo su trabajo.

### Paso 6 · Evaluar: la misma métrica para el honesto y el descuidado

```text title="▸ deberías ver al correr 29_caso_retail.py (recortado)"
» quiero aretes dorados por menos de 25 soles
  filtros: {'presupuesto': 25.0, 'categoria': 'aretes', 'color': 'dorado'}
  - Aretes Argolla Mediana Dorado a S/19.90 (SKU AR-001)
  guardrail de precios: OK

» un collar de zircón por menos de 10 soles
  No encontré productos que cumplan lo que pides. …
  guardrail de precios: OK          ← "no tengo" también es honesto

=== EVAL · asistente honesto vs descuidado (misma métrica) ===
  honesto    (filtros duros + grounding): 100%
  descuidado (ignora el presupuesto)    : 50%
  → la métrica atrapa al descuidado. Sin eval, lo atrapa un cliente.
```

### Paso 7 · De la maqueta a producción (ya lo tienes construido)

Este pipeline se monta tal cual sobre el stack del [proyecto_llmops](/recurso/llmops): servirlo por SSE con FastAPI ([c17](/concepto/17-repo-productivo)/[c25](/concepto/25-frontend-chat-sse)), guardrails de entrada y salida ([c23](/concepto/23-seguridad-red-teaming)), caché semántico para las preguntas repetidas, A/B del prompt de la vendedora ([c24b](/concepto/24b-feedback-a-b)) y trazas con coste por consulta ([c16](/concepto/16-observabilidad-y-costo)). Lo que añadirías con presupuesto: embeddings + re-ranking reales ([c12](/concepto/12-recuperar-re-rankear)) en vez del solape de términos, multi-query ([c20](/concepto/20-rag-avanzado)) para el vocabulario de la calle ("aros"/"aretes" — ya lo probaste en miniatura con los sinónimos), "busca por foto" con visión ([c22](/concepto/22-multimodal)), y la integración con el inventario por tienda — que es donde el caso 3 del menú se encuentra con este.

### Paso 8 · El build organizado: de la maqueta al proyecto

📁 El proyecto entero: **curso_ejemplos/proyecto_retail/** — corre 100% offline; su README trae el diagrama y el mapa "quiero X → miro Y"✓ 61 tests

Todo lo anterior vive, además, como un **proyecto con estructura de producción** —la misma relación que el [proyecto_llmops](/recurso/llmops) tiene con los conceptos sueltos—. Ahí el LLM está cableado de verdad: la intención ya no es un regex sino `llm.with_structured_output(FiltrosCompra)` (el [c05](/concepto/05-salida-estructurada)), y la respuesta la redacta el modelo con tono de vendedora. Lo que **no** cambia es la interfaz: *petición → filtros → productos → texto*. Por eso subir el eslabón no reescribe el pipeline —y el guardrail de precios sigue vigilando igual, con el mismo `respuesta_es_fiel`—.

El lazo que cierra el caso está en `app/agent.py`: el LLM redacta, el guardrail verifica, y si cita un precio que no existe se **reintenta una vez** con la lista de precios permitidos; si vuelve a fallar, gana el **fallback determinista** (fiel por construcción). Una respuesta con un precio inventado **no puede salir**. Alrededor, las capas del estándar LLMOps: guardrails de entrada/salida, caché semántico, A/B de prompts con feedback por variante, trazas con coste, y un **CI gate** con cero tolerancia al precio inventado. El *por qué* de cada decisión está en `proyecto_retail/docs/adr/`.

<Box kind="warn" label="▲ Precio y stock JAMÁS salen del modelo">

El catálogo real cambia **a diario** (colecciones por temporada, promos que entran y salen). Por eso este caso es **RAG y no fine-tuning** —la biblioteca, no la escuela ([c21](/concepto/21-fine-tuning-vs-rag))—: afinar un modelo con los precios de julio es fabricar un mentiroso para agosto. Y el LLM solo **redacta** sobre lo recuperado: un precio inventado en retail no es una anécdota, es un reclamo — y en Perú, un problema con Indecopi.

</Box>

<Avoid label="⛔ Cuándo NO hacer esto">

- No metas un LLM donde basta un **WHERE**: filtrar por precio y categoría es SQL de toda la vida. El modelo entra donde hay *lenguaje* (entender la petición, redactar), no donde hay aritmética.
- No golpees el endpoint público **sin respeto**: una descarga puntual para aprender es razonable; scraping agresivo o uso comercial de datos ajenos, no. La regla del c23 aplica también a ti como consumidor de datos.
- No prometas **stock de tienda física** si tu fuente es solo el e-commerce: son inventarios distintos. Sin la fuente, el asistente debe decir "consúltalo en tu tienda" — honestidad antes que cobertura.

</Avoid>

<Box kind="practice" label="▸ Para practicar (con los datos de verdad)">

Descarga el catálogo real y corre el pipeline entero sobre él: `curl -s 'https://sifrah.com/products.json?limit=250' > catalogo.json`, carga el JSON y pásalo por `cargar_catalogo(datos["products"])`. Verás fallar cosas — categorías nuevas que tus reglas no conocen, títulos con formatos raros. **Ese es el ejercicio**: ajustar el ETL hasta que el eval vuelva a 100%.

**Mini-reto** · añade el filtro **`en_promo`** de punta a punta: que "algo en oferta" salga de `extraer_filtros` como un filtro tipado y que `buscar_productos` lo trate como lo que es — una restricción **dura**, no una preferencia de ranking.

**Criterio de aceptación:** `extraer_filtros("aretes en oferta por menos de 30 soles")` devuelve `en_promo=True` junto a la categoría y el presupuesto; ninguna petición sin la palabra clave activa el filtro (`en_promo` queda en `None`, **no** en `False`); y `buscar_productos` no devuelve jamás un producto con `en_promo=False` cuando el filtro está activo. El guardrail `respuesta_es_fiel` y el eval siguen en 100%.

<Solution summary="Ver una solución">

```python title="solución · un filtro nuevo sin tocar el resto del pipeline"
_PROMO = ("en oferta", "en promo", "rebajado", "descuento", "barato")

def extraer_filtros(peticion):
    texto = _sin_tildes(peticion.lower())
    filtros = {"presupuesto": None, "categoria": None,
               "color": None, "en_promo": None}   # None = "no lo pidió"
    # …presupuesto, categoría y color igual que antes…
    if any(clave in texto for clave in _PROMO):
        filtros["en_promo"] = True                # solo se activa si lo PIDE
    return filtros
```

```python title="solución · el WHERE, junto a los otros filtros duros"
# Dentro de buscar_productos, con los demás filtros duros (NO en afinidad):
if filtros.get("en_promo"):                       # `.get() is None` → no filtra
    candidatos = [p for p in candidatos if p["en_promo"]]
```

```python title="solución · los tests que fijan el contrato"
def test_extrae_promo():
    f = extraer_filtros("aretes en oferta por menos de 30 soles")
    assert f["en_promo"] is True and f["categoria"] == "aretes" and f["presupuesto"] == 30.0

def test_no_inventa_promo():
    # Sin la palabra clave el filtro NO se activa: None, no False.
    assert extraer_filtros("aretes dorados")["en_promo"] is None

def test_promo_es_filtro_duro():
    catalogo = cargar_catalogo()
    r = buscar_productos({"en_promo": True}, catalogo)
    assert all(p["en_promo"] for p in r)          # ni uno fuera de promo
```

El detalle que importa: **`None` y `False` no son lo mismo**. `None` significa "el cliente no lo mencionó" (no filtras); `False` significaría "quiero productos que NO estén en oferta" (filtras al revés). Confundirlos hace que toda petición normal empiece a excluir las promociones en silencio — el tipo de bug que solo se ve en la factura de conversión.

Y el mismo criterio del presupuesto: si nada en promo cumple, la respuesta es **lista vacía**. Ofrecer un producto a precio lleno cuando pidieron oferta es exactamente el sustituto inválido que este concepto prohíbe.
