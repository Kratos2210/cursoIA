Nivel Básico · Módulo 01

Tu primer modelo

📋 Copia y ejecuta: curso_ejemplos/01_primer_modelo.py✓ cubierto por tests

🎯 Al terminar sabrás: hablar con el modelo con .invoke() y distinguir los tipos de mensaje.✅ Necesitas: Módulos 00–0b.⏱️ ~20 min

Todo empieza con una llamada al modelo. Un chat model recibe mensajes y devuelve una respuesta. El método clave es .invoke().

◈ Definición · Modelo de chat (chat model)

Un modelo de chat es un LLM al que no le hablas con un texto suelto, sino con una lista de mensajes con rol, y que te devuelve un mensaje más. Toda la librería está construida sobre esa forma: mensajes entran, mensaje sale.

Esa es la diferencia con "un LLM" a secas. El LLM es el modelo entrenado; el chat model es la envoltura de LangChain que le da una interfaz uniforme (.invoke(), .batch(), .stream()) idéntica en Gemini, OpenAI o Claude.

token
La unidad en la que el modelo lee y escribe: un trozo de palabra (≈ 4 caracteres). No cuentas letras ni palabras, cuentas tokens — porque es lo que te cobran y lo que limita cuánto texto le cabe.
ventana de contexto
El máximo de tokens que el modelo puede tener "a la vista" en una llamada: pregunta + historial + documentos + su propia respuesta. Cuando se llena, algo hay que recortar.
temperature
Cuánta aleatoriedad se permite al elegir el siguiente token. 0 = la misma respuesta siempre; 0.9 = variada. No es "inteligencia", es dispersión.

Los tipos de mensaje

Una conversación es una lista de mensajes con roles distintos. Entenderlos es clave para todo lo que sigue (memoria, tools, agentes):

  • SystemMessage: las reglas y personalidad ("eres un tutor paciente").
  • HumanMessage: lo que dice el usuario.
  • AIMessage: lo que responde el modelo (aquí también viajan los tool_calls).
  • ToolMessage: el resultado de ejecutar una herramienta (Módulo 08).
◆ Bueno saber

El parámetro temperature controla la creatividad: 0 = preciso y repetible (clasificar, calcular, usar tools); 0.7–1 = variado (redactar, conversar). En LangChain 1.x existe también init_chat_model("gemini-2.0-flash") para crear cualquier modelo cambiando solo el nombre.

▸ Para practicar

Cambia el SystemMessage a "eres un pirata" y observa cómo cambia el tono sin tocar la pregunta. Luego prueba temperature=0 vs 0.9 repitiendo la misma consulta 3 veces.

Nivel Básico · Módulo 02

Prompts + LCEL: la línea de ensamblaje

📋 Copia y ejecuta: curso_ejemplos/02_prompts_lcel.py✓ cubierto por tests

🎯 Al terminar sabrás: armar cadenas con plantillas de prompt y el operador | (LCEL).✅ Necesitas: Módulo 01.⏱️ ~25 min

Un prompt template es un molde con huecos {variables}. Y aquí aparece la idea central de LangChain moderno: LCEL, que conecta pasos con el operador tubería |.

◈ Definición · LCEL

LCEL (LangChain Expression Language, Lenguaje de Expresión de LangChain) es una forma declarativa de construir cadenas de procesamiento: en lugar de escribir paso a paso cómo se llama a cada pieza, declaras el orden en que se conectan y LangChain se encarga del resto.

"Declarativo" tiene una consecuencia práctica y no es decoración: como LangChain conoce la forma completa de la cadena antes de ejecutarla, puede darte gratis paralelismo en batch, streaming token a token, versiones asíncronas y reintentos — sin que tú escribas nada de eso.

La magia del operador tubería (|)

La sintaxis imita las tuberías de Unix: | encadena componentes de modo que la salida de uno es la entrada del siguiente. Una cadena básica tiene tres bloques:

Prompt (plantilla)  |  Modelo (LLM)  |  Parser (analizador de salida)

PromptTemplate
El molde de tus instrucciones. En vez de un mensaje fijo, defines una plantilla con variables ("Traduce al {idioma}: {texto}") y reutilizas la misma estructura para entradas distintas.
Model
El cerebro: el modelo de lenguaje (Gemini, GPT, Claude). Recibe el prompt ya rellenado y genera la respuesta.
OutputParser
El formateador. Toma la respuesta cruda del modelo (un AIMessage) y la convierte en algo que tu programa pueda usar directo: texto plano con StrOutputParser, o un objeto/JSON con parsers estructurados.
◆ Analogía

El | es una línea de ensamblaje: el dato entra por la izquierda y avanza de estación en estación. prompt arma el mensaje → modelo lo responde → parser limpia la salida.

StrOutputParser() convierte la respuesta del modelo en texto plano, para no escribir .content todo el tiempo.

▸ Para practicar

Nivel Básico · Módulo 03

La interfaz unificada: invoke / batch / stream

📋 Copia y ejecuta: curso_ejemplos/03_interfaz_unificada.py✓ cubierto por tests

🎯 Al terminar sabrás: ejecutar la misma cadena con invoke, batch y stream.✅ Necesitas: Módulo 02.⏱️ ~20 min

Toda cadena LCEL entiende los mismos verbos. No reescribes nada: es el mismo objeto cadena, tres formas de ejecutarlo.

◈ Definición · Interfaz unificada (Runnable)

La interfaz unificada es el contrato que cumplen todas las piezas de LangChain: un prompt, un modelo, un parser y una cadena entera exponen exactamente los mismos métodos. Ese contrato tiene nombre: Runnable.

Es lo que hace posible el | del módulo anterior. Puedes conectar A con B porque ambos prometen entender los mismos verbos, y una cadena de dos Runnables vuelve a ser un Runnable — por eso las cadenas se anidan sin límite.

invoke(entrada)
Una entrada, una salida. El modo normal.
batch([e1, e2, …])
Muchas entradas en paralelo. No es un for: las llamadas salen a la vez, así que N preguntas tardan casi lo que una.
stream(entrada)
La salida llega por trozos según se genera, en vez de esperar al final. Es lo que hace que un chat "escriba" delante de ti.
ainvoke / abatch / astream
Los tres gemelos asíncronos (la a es de async): mismo comportamiento, pero liberan el programa mientras esperan a la API. Módulo 09.
◆ La versión asíncrona

Cada verbo tiene su gemelo async con una a delante: ainvoke, abatch, astream. Sirven para no bloquear el programa mientras esperas a la API (lo profundizamos en el Módulo 09).

▲ El await no va suelto

await solo funciona dentro de una función async def. Si pegas await cadena.ainvoke(...) tal cual en un script normal, Python te lanza un SyntaxError: 'await' outside function. Para probarlo en un archivo, envuélvelo en una función async y arráncala con asyncio.run(mi_funcion()) — justo como hace el Módulo 09. (En un notebook de Jupyter sí puedes escribir await a nivel de celda: el notebook ya corre dentro de un bucle async.)

▸ Para practicar

Nivel Básico · Módulo 04

Memoria: que no olvide la conversación

📋 Copia y ejecuta: curso_ejemplos/04_memoria.py✓ cubierto por tests

🎯 Al terminar sabrás: darle memoria a una conversación reenviando el historial.✅ Necesitas: Módulo 02.⏱️ ~25 min

Un LLM es amnésico: cada .invoke() es independiente. Para que "recuerde", tú le reenvías el historial en cada turno. La pieza que reserva ese hueco es MessagesPlaceholder.

◈ Definición · Memoria

Memoria, en LangChain, no es que el modelo guarde nada. El modelo no guarda nada: es una función sin estado que recibe mensajes y devuelve uno. La memoria es una estructura tuya —una lista de mensajes— que reenvías completa en cada llamada para que el modelo "se acuerde".

Entender esto explica dos cosas de golpe: por qué la conversación cuesta más cara turno a turno (reenvías todo el historial cada vez, y pagas por token) y por qué llega un momento en que hay que resumir o recortar (la ventana de contexto se llena).

MessagesPlaceholder
El hueco reservado dentro del prompt donde se inyectará la lista de mensajes anteriores. Sin él, tu plantilla no tendría dónde poner el historial.
historial
La lista de HumanMessage / AIMessage acumulados. Vive en tu programa (una lista, una base de datos, un checkpointer), nunca en el modelo.
thread_id
La etiqueta que separa una conversación de otra. Dos usuarios con el mismo agente y distinto thread_id no se pisan el historial. Aparece a partir del Módulo 10.
◆ Analogía

Es como un chat de WhatsApp: cada mensaje ve todo el hilo arriba. Aquí tú "subes el hilo" reenviando history. En el Módulo 10 verás cómo LangGraph hace esto automáticamente.

◈ Definición · Salida estructurada

Salida estructurada es obligar al modelo a responder con un objeto de forma conocida en lugar de prosa libre. Tú declaras la forma (qué campos hay, de qué tipo, cuáles son obligatorios) y recibes un objeto de Python ya validado, no un texto que tengas que interpretar con expresiones regulares.

Pydantic
La librería con la que se declara la forma: una clase con campos tipados y descripciones. Esas descripciones las lee el modelo — son parte del prompt, no comentarios.

Un molde que obliga a rellenar es un molde que invita a alucinar.

📋 Copia y ejecuta: curso_ejemplos/06_runnables.py✓ cubierto por tests

◈ Definición · Runnable

Un Runnable es cualquier pieza que se puede meter en una cadena LCEL: un prompt, un modelo, un parser, una función tuya, o una cadena entera. Solo tiene que cumplir el contrato del Módulo 03 (invoke, batch, stream).

La propiedad que lo vuelve poderoso es que es cerrado bajo composición: si a y b son Runnables, a | b también lo es. Por eso puedes tratar un RAG completo como si fuera un solo eslabón dentro de una cadena más grande.

Ejecuta varias ramas a la vez sobre la misma entrada y devuelve un diccionario con la salida de cada una. Un diccionario de Python dentro de una cadena ya se interpreta como esto.

Convierte una función normal de Python en un eslabón de la cadena. Es la puerta por la que entra tu propio código: limpiar, filtrar, formatear.

Corre varias ramas a la vez y junta sus salidas en un diccionario.

RunnablePassthrough

Pasa la entrada tal cual, sin tocarla (clave en RAG para conservar la pregunta).

RunnableLambda

Mete cualquier función de Python dentro de la cadena.

Una cadena RAG (Módulo 11) es literalmente esto: {"context": retriever | unir, "question": RunnablePassthrough()}. Recuperas contexto en una rama y conservas la pregunta en la otra, en paralelo.

◈ Definición · Herramienta (tool)

Una herramienta es una función de Python descrita de forma que el modelo pueda decidir cuándo usarla y con qué argumentos. Nada más. El modelo no ejecuta código: pide que se ejecute, y tu programa obedece o no.

@tool
El decorador que convierte la función en herramienta. Lee el nombre, los tipos de los argumentos y el docstring para armar la descripción.
el docstring es el prompt
La descripción no es documentación para ti: es lo único que el modelo lee para elegir. Un docstring vago produce un agente que elige mal. Escríbelo pensando en quién lo va a leer.

◆ Analogía

Darle herramientas al modelo es como darle a un empleado nuevo acceso al sistema de la empresa. Él conoce las opciones disponibles y decide cuál pedir para resolver tu encargo — pero quien finalmente aprieta el botón eres tú (tu código). El empleado no ejecuta nada por su cuenta: solicita, y tú autorizas o rechazas.

El docstring no es documentación: es programación. El modelo decide cuándo usar la herramienta leyendo esa descripción, y usa los nombres/tipos de los parámetros (precio: float) para rellenar los datos. Docstring vago → agente que se equivoca.

Routing: el ciclo completo de un agente

📋 Copia y ejecuta: curso_ejemplos/08_routing.py✓ cubierto por tests

🎯 Al terminar sabrás: cerrar el ciclo completo de tool calling (A→D) a mano.✅ Necesitas: Módulo 07.⏱️ ~35 min

Con llm.bind_tools() le entregas el "cinturón". El modelo decide si responder directo o pedir una herramienta (eso es routing). Pero pedirla es solo la mitad: el ciclo real tiene cuatro pasos.

◈ Definición · Routing y tool calling

Routing es dejar que el modelo decida el camino que toma la ejecución, en vez de decidirlo tú con un if. Le presentas las opciones (las herramientas) y él elige: responder directo, o pedir una.

Tool calling es el mecanismo concreto con el que expresa esa elección, y es un ciclo de cuatro pasos, no una llamada. Casi todos los errores de principiante consisten en olvidar el paso D.

A · bind_tools
Le "atas" las herramientas al modelo: sus nombres y descripciones viajan en cada llamada.
B · el modelo pide
Devuelve un AIMessage con tool_calls en vez de texto. Todavía no pasó nada en el mundo real.
C · tú ejecutas
Tu código llama a la función de Python con los argumentos que pidió. Aquí es donde validas, autorizas o rechazas.
D · le devuelves el resultado
Un ToolMessage con la respuesta, y vuelves a invocar al modelo. Sin este paso el modelo nunca ve el resultado y no puede redactar la respuesta final.
A
Pregunta
El humano escribe.
→
B

El modelo pide una tool.
→
C

→

El modelo responde con el dato real.
◆ Analogía

El ciclo A→D es como un mesero que lleva tu pedido a la cocina y te trae el plato. El cliente (el modelo) pide, pero no entra a la cocina: quien cocina —quien ejecuta la herramienta— eres tú. El mesero solo transmite el pedido y luego trae el resultado a la mesa. Por eso el modelo nunca toca tu código: solo pide, y espera que le devuelvas el plato.

El ciclo, línea por línea

Ese bloque es corto pero cada línea hace algo concreto. Vale la pena leerlo despacio, porque este mismo ciclo es el que LangGraph automatiza en el Módulo 10:

  • mapa = {t.name: t for t in herramientas} — es una dict comprehension (no la vimos en el Módulo 0b): construye un diccionario nombre → herramienta en una sola línea. Equivale a un for con asignaciones: recorrer la lista y por cada herramienta t guardar mapa[t.name] = t. Lo necesitas porque el modelo pide la tool por su nombre (un texto), y con este diccionario pasas de ese texto a la función real.
  • llm_tools = llm.bind_tools(herramientas) — (A) le "ata" las herramientas al modelo: a partir de aquí, cada llamada lleva los nombres y docstrings de las tools.
  • ai = llm_tools.invoke(mensajes) — (B) el modelo decide. Devuelve un AIMessage; si quiere una tool, viene con ai.tool_calls lleno en vez de texto.
  • for llamada in ai.tool_calls: — recorremos cada petición que hizo el modelo (puede pedir más de una).
  • mapa[llamada["name"]].invoke(llamada["args"]) — (C) el corazón del paso: llamada["name"] es el texto con el nombre pedido; mapa[...] lo traduce a la función real; y le pasamos llamada["args"] (el diccionario de argumentos que el modelo eligió). Aquí, y solo aquí, se ejecuta tu código.
  • mensajes.append(ToolMessage(content=str(resultado), tool_call_id=llamada["id"])) — (D, parte 1) guardamos el resultado atado al id de la petición: ese tool_call_id es el hilo que une "lo que pidió" con "lo que respondió".
  • llm_tools.invoke(mensajes) (la última línea) — (D, parte 2) volvemos a invocar al modelo, ahora con el resultado ya en la conversación. Recién con esto puede redactar la respuesta final.
▲ El error típico

Muchos se quedan en el paso B e imprimen el tool_calls crudo. Sin C y D no tienes un agente: tienes media función. El ToolMessage con su tool_call_id es el hilo que une pedido y resultado.

▸ Para practicar

Añade una segunda herramienta y haz una pregunta que necesite las dos. Como iteramos sobre ai.tool_calls, el código ya lo soporta.

◈ Definición · Resiliencia y asincronía

Resiliencia es diseñar asumiendo que las llamadas van a fallar. No es evitar el fallo: es decidir de antemano qué pasa cuando ocurra, en lugar de que se caiga toda la petición.

Asincronía es otra cosa distinta, aunque se estudien juntas: no hace nada más rápido, hace que tu programa no se quede parado mientras espera. Una llamada al LLM tarda segundos, y el 99% de ese tiempo la CPU no hace nada — el await aprovecha ese hueco para atender otra cosa.

with_fallbacks([b])
Si la pieza principal falla, la cadena reintenta con otra pieza (otro modelo, otro proveedor). La llanta de repuesto.
with_retry()
Reintenta lo mismo unas cuantas veces, esperando cada vez un poco más. Sirve para fallos temporales como un 429; es inútil si tu prompt está mal.
429 RESOURCE_EXHAUSTED
El error de cuota. En este curso lo verás seguido con el plan gratuito de Gemini: no es un bug de tu código, es el proveedor diciendo "más despacio".
async / await
La sintaxis de Python para "esto tarda, sigue con otra cosa mientras". Combinado con asyncio.gather lanza muchas llamadas a la vez.
◆ Analogía

with_fallbacks es la llanta de repuesto: si un modelo se pincha, la cadena sigue rodando con otro. with_retry es volver a tocar la puerta unas veces antes de irte.

RAG (Retrieval-Augmented Generation) le da al modelo tus documentos. Es un examen a libro abierto: busca los fragmentos relevantes y se los pasa como contexto antes de responder.

◈ Definición · RAG

RAG (Retrieval-Augmented Generation, generación aumentada por recuperación) es una técnica para que el modelo responda usando documentos tuyos que nunca vio en su entrenamiento. No se reentrena nada: antes de preguntarle, buscas los fragmentos relevantes y se los pegas en el prompt como contexto.

Resuelve tres problemas de un golpe: el modelo no conoce tus datos privados, su conocimiento tiene fecha de corte, y cuando no sabe algo tiende a inventarlo. Con RAG, la respuesta se apoya en texto que tú controlas — y puedes exigirle que cite de dónde salió.

embedding
Un texto convertido en una lista de números que captura su significado. Dos textos que hablan de lo mismo tienen embeddings cercanos, aunque no compartan ni una palabra.
vector store
La base de datos que guarda esos números y sabe encontrar los más cercanos a una consulta. Es lo que hace la búsqueda "por significado" en vez de por coincidencia literal.
chunk
Un trozo del documento original. Se trocea porque no cabe entero en el prompt y porque un fragmento enfocado recupera mejor que un capítulo completo.
retriever
La pieza que recibe la pregunta y devuelve los k chunks más relevantes. Es un Runnable, así que entra en una cadena LCEL como cualquier otro eslabón.

Casi todo el mundo dibuja RAG como una sola tubería, y por eso confunde dos cosas que ocurren en momentos distintos. Son dos caminos: uno se recorre una vez, cuando preparas tus documentos; el otro, en cada pregunta. Este es el mapa completo — los módulos 11 y 12 lo recorren entero, pieza por pieza.

◈ Definición · Búsqueda híbrida y re-ranking

La búsqueda híbrida combina dos formas de buscar que fallan de maneras distintas: la vectorial (por significado) y la léxica (por palabras exactas). La vectorial encuentra "cifrado" cuando preguntas por "encriptación", pero se pierde con un código como DQ-014. La léxica hace justo lo contrario. Juntas, se tapan los huecos.

El re-ranking es un segundo filtro: recuperas muchos candidatos rápido y baratos, y luego un modelo más caro y más preciso los reordena para quedarse con los mejores. Recuperar es rápido y tonto; re-rankear es lento y listo. Por eso van en ese orden.

BM25
El algoritmo clásico de búsqueda por palabras clave. Premia los términos raros y penaliza los documentos largos. No entiende sinónimos — y ahí está su virtud: no "interpreta" tu código de error.
RRF (Reciprocal Rank Fusion)
La receta para fusionar dos rankings sin comparar puntuaciones incomparables. Solo mira la posición: un documento que salió 2.º en ambas listas gana a uno que salió 1.º en una y 40.º en la otra.
cross-encoder
El re-ranker típico: en vez de comparar dos vectores ya calculados, lee pregunta y chunk juntos. Mucho más preciso y mucho más lento — por eso solo se le dan 20 candidatos, no 10.000.
precision@k
De los k resultados que devolviste, cuántos eran realmente relevantes. Es la métrica que convierte "creo que mejoró" en un número. Mídela antes y después de cada cambio.

Chunking: el corte importa más de lo que parece

Todo lo que el sistema podrá responder depende de cómo cortaste los documentos. Dos estrategias que ya usaste:

  • Por párrafos (Módulo 11): respeta unidades de sentido. Ideal si el documento está bien estructurado.
  • Por caracteres con solapamiento (tu proyectorag): corta cada N caracteres y retrocede un poco en cada corte, para que ninguna frase quede huérfana de contexto.

En producción, RecursiveCharacterTextSplitter (Módulo 11) combina ambas ideas: intenta cortar por párrafo, si no puede corta por frase, y solo como último recurso por carácter.

Re-ranking: el segundo filtro

El buscador vectorial es rápido pero impreciso: entre sus primeros resultados hay joyas y basura mezcladas. Un re-ranker es un segundo filtro, más lento pero mucho más certero, que reordena y deja arriba lo verdaderamente relevante.

◆ Por qué acierta más (y tarda más)

El buscador vectorial compara huellas precalculadas: nunca lee tu pregunta junto al documento. El cross-encoder sí: lee pregunta + fragmento juntos y puntúa qué tan bien uno responde al otro. Es como seleccionar personal: filtrar currículums por palabras clave es rápido; entrevistar acierta mucho más, pero no puedes entrevistar a mil. Por eso primero recuperas 20 y solo "entrevistas" a esos.

Búsqueda híbrida (denso + palabras clave)

La búsqueda por significado falla con códigos exactos ("ISO-27001", un SKU, un nombre propio); la de palabras (BM25) falla con sinónimos. Combinarlas cubre los huecos de ambas.

¿Y cómo se mezclan dos rankings con puntajes incompatibles (BM25 devuelve "7.3", el vectorial "0.42")? No se suman los puntajes: se usa el puesto. La técnica se llama RRF (Reciprocal Rank Fusion) y cabe en seis líneas — quien aparece en ambas listas, gana:

▲ Lo que RRF premia (y lo que NO)

Casi todo el mundo dice que RRF "premia al que queda equilibrado en ambas listas". Es falso, y se demuestra con una calculadora. Con k=60, un documento que queda 1º y 3º suma 1/61 + 1/63 = 0.032266; uno que queda 2º y 2º suma 1/62 + 1/62 = 0.032258. Gana el extremista, no el consistente: la curva 1/(k+puesto) es convexa, así que el promedio de los extremos supera al del medio.

Lo que RRF premia de verdad es estar presente en ambas listas. Un documento 2º y 2º (0.032258) aplasta a uno que fue 1º en una lista pero que la otra ni vio (1/61 = 0.016393): la ausencia no suma nada. Ese, y no el equilibrio, es el mecanismo. Hay un test que lo fija en tests/test_offline.py — de hecho, ese test corrigió a quien escribió esta explicación.

Tres formas de fallar que este pipeline no te cuenta

Corre el ejemplo con la pregunta "¿Cómo pido la devolución de mi dinero?" — el documento habla de reembolso. Verás fallar tres cosas a la vez, y cada una es una lección de producción:

fallo 1

Sinónimos

"devolución" y "reembolso" no comparten letras: su coseno es 0.0. El chunk correcto es invisible. Y ojo: el buscador "vectorial" del ejemplo cuenta palabras, así que falla igual que BM25.

fallo 2

Stopwords

¿Quién gana? El chunk del título, que no responde nada. Solo comparte la palabra "de" — pero es tan corto que la normalización por longitud de BM25 lo catapulta.

fallo 3

Empates silenciosos

Ninguna palabra casa, así que el re-ranker puntúa 0.0 a todos y desempata por el índice del chunk. Devuelve tres finalistas con toda la confianza del mundo. Es un orden arbitrario.

▲ El tercero es el peligroso

Los fallos 1 y 2 se ven. El 3 no: el sistema no lanza ningún error, no avisa de nada, simplemente devuelve basura ordenada. Por eso un re-ranker de producción devuelve también el puntaje, no solo el orden — para que quien lo llama pueda decir "todos por debajo del umbral: no tengo respuesta". Un ranking sin puntajes es una opinión disfrazada de dato.

La cura del fallo 1 son embeddings de verdad (los del Módulo 11), que sí colocan "devolución" y "reembolso" cerca. La del 2, eliminar stopwords antes de indexar. La del 3, umbrales. Y hay un cuarto fallo, más sutil, que descubres al medir: fusionar dos buscadores que se equivocan igual no arregla nada — RRF fusiona opiniones, y aquí las dos opiniones son la misma (coincidencia léxica). Un híbrido de verdad combina señales independientes: léxica + semántica.

¿Recupera bien? No lo adivines: mídelo

La métrica más simple es precision@k: de los k fragmentos que trajiste, ¿cuántos eran realmente útiles para responder? Si traes 4 y solo 1 sirve, tu precisión es 25% — y los otros 3 son ruido que confunde al modelo y cuesta tokens. Para medirla necesitas un banco de preguntas con su fragmento correcto conocido (tu proyectorag/preguntas.txt es exactamente eso). En el Módulo 16 convertimos ese banco en una evaluación automática.

▲ Compromiso latencia ↔ calidad

Cada capa (más k, re-ranker, híbrido) mejora la calidad del ranking pero suma latencia. Regla práctica: recupera barato y ancho (20 candidatos con vectorial+BM25, milisegundos) y refina caro y angosto (re-rankear solo esos 20, no todo el corpus). En producción se busca el punto donde la precisión sube sin que la respuesta tarde demasiado — y se mide, no se supone.

Mídelo de verdad sobre datos_rag.txt. Con 4 preguntas fáciles (que usan las mismas palabras del documento), las cuatro configuraciones dan 100%: ese dataset no mide nada. ◈ Definición · LangGraph y StateGraph

LangGraph es la librería para escribir flujos de IA como un grafo en vez de como una línea. La diferencia con LCEL no es de estilo: una cadena LCEL no puede volver hacia atrás, y un grafo sí. Ciclos, ramas condicionales, pausas y reanudaciones solo existen aquí.

Un StateGraph es ese grafo con una regla añadida: hay un estado compartido que todos los nodos leen y actualizan. Un nodo no recibe la salida del anterior — recibe el estado completo y devuelve el trozo que quiere cambiar.

estado
El diccionario que viaja por el grafo (típicamente con una lista messages). Cada nodo devuelve un fragmento y LangGraph lo mezcla con lo que ya había.
nodo (add_node)
Una función de Python: recibe el estado, devuelve una actualización. Un nodo puede llamar al LLM, ejecutar tools o no hacer nada con IA.
arista (add_edge)
Una flecha fija: "de aquí siempre se va allá". START y END son los extremos que pone LangGraph.
arista condicional
Una flecha que decide: una función mira el estado y devuelve el nombre del siguiente nodo. Es lo que crea el ciclo del agente (¿hay tool_calls? → tools; si no → END).
checkpointer
Guarda el estado después de cada nodo. Es lo que permite reanudar tras un reinicio, inspeccionar con app.get_state() y hacer human-in-the-loop.

◈ Definición · Human-in-the-loop

Human-in-the-loop (humano en el bucle) es insertar una aprobación humana obligatoria dentro de la ejecución del agente, en el punto exacto donde una acción se vuelve irreversible.

▲ Persistencia en producción

MemorySaver guarda el estado en RAM (se pierde al reiniciar). Para producción usa un checkpointer persistente como SqliteSaver o PostgresSaver: así una conversación (o una pausa human-in-the-loop) sobrevive a reinicios y caídas. El JSON de arriba muestra la mecánica; los checkpointers oficiales hacen eso mismo, con transacciones y por thread_id.

◈ Definición · MCP

MCP (Model Context Protocol, Protocolo de Contexto del Modelo) es un protocolo, no una librería: un acuerdo sobre cómo un agente pregunta "¿qué sabes hacer?" y cómo pide que se haga. Cualquiera puede implementarlo en cualquier lenguaje.

El problema que resuelve es de multiplicación: sin un estándar, conectar M agentes con N herramientas cuesta M×N integraciones a medida. Con MCP cuesta M+N — cada agente habla el protocolo una vez, cada herramienta lo expone una vez.

servidor MCP
Envuelve una capacidad (tu base de datos, GitHub, un sistema interno) y la publica según el protocolo. Puede ser un proceso local o remoto.
cliente MCP
Vive del lado del agente. Descubre qué ofrece el servidor y traduce esas capacidades a herramientas que el LLM puede pedir.
tools · resources · prompts
Las tres cosas que un servidor puede exponer: acciones que se ejecutan, datos de solo lectura y plantillas reutilizables. Ver abajo.
transporte
Cómo viajan los mensajes: stdio (el servidor es un subproceso tuyo) o HTTP (está en otra máquina). El protocolo es el mismo; cambia el riesgo.

Estándar

Una sola forma de conectar cualquier herramienta o dato, sin adaptadores a medida.

Seguro

Intercambio controlado de contexto y comandos: evita ejecuciones inseguras y exfiltración de datos.

Escalable

Sumas capacidades agregando servidores, sin tocar el código del agente.

◆ Analogía

MCP es el puerto USB-C de los agentes: antes cada herramienta tenía su cable propio; ahora todas usan el mismo conector estándar, y tú controlas qué se enchufa y con qué permisos.

Qué expone un servidor MCP

Un servidor MCP puede ofrecer tres tipos de capacidades. Cuando evalúes un servidor ajeno (o diseñes el tuyo), pregúntate cuáles de las tres necesita realmente:

Tools

Acciones que el agente puede ejecutar: buscar, calcular, escribir en un sistema. Las más comunes — y las más delicadas.

Resources

Datos de solo lectura que el agente puede consultar: archivos, tablas, documentación.

Prompts

Plantillas reutilizables que el servidor ofrece listas para usar ("analiza este log con este formato").

📋 Copia y ejecuta: curso_ejemplos/15_supervisor_multiagente.py — 100% offline, no gasta cuota✓ cubierto por tests

🎯 Al terminar sabrás: repartir el trabajo entre agentes especialistas coordinados por un supervisor.✅ Necesitas: Módulo 13.⏱️ ~35 min

Un agente con demasiadas herramientas se vuelve tonto, y la cura es repartir el trabajo entre especialistas coordinados por un supervisor. Es el principio de divide y acota aplicado al razonamiento del sistema. La misma idea, una escala más arriba —repartir el sistema en servicios independientes— es el Módulo 15b.

El problema: el agente que sabe demasiado

Le das 3 herramientas a un agente y elige bien. Le das 12 y empieza a fallar: su prompt del sistema crece hasta ocupar miles de tokens, las descripciones de las tools compiten entre sí, y el modelo confunde buscar_normativa con buscar_reporte. No es que el modelo sea malo: es que le pediste que fuera experto en todo a la vez.

◆ Analogía

Es la diferencia entre un médico general con doce especialidades falsas y un hospital: recepción escucha tu problema y te manda a cardiología o a traumatología. El recepcionista no sabe de corazones — sabe a quién preguntarle. Y cada especialista tiene su propio consultorio, sus propios instrumentos y su propia forma de equivocarse, acotada.

El patrón supervisor

Un supervisor es un nodo que no hace el trabajo: decide quién lo hace. Los especialistas responden y le devuelven el control. El bucle se repite hasta que ya no queda trabajo pendiente.

◈ Definición · Sistema multiagente y patrón supervisor

Un sistema multiagente es varios agentes especializados, cada uno con su propio prompt y su propio puñado de herramientas, coordinados para resolver algo que uno solo haría mal. No se reparte el trabajo por moda: se reparte porque la calidad de decisión de un LLM cae cuando le das demasiadas opciones.

El patrón supervisor es la forma más simple de coordinarlos: un nodo central enruta hacia el especialista adecuado, recibe su respuesta y vuelve a decidir. El supervisor no sabe hacer nada — sabe a quién preguntarle.

supervisor
El nodo enrutador. Su única salida útil es un nombre: a qué especialista le toca ahora, o END si ya terminó.
especialista (worker)
Un agente acotado: pocas herramientas, un dominio, un prompt corto. Se equivoca, pero se equivoca dentro de un terreno pequeño.
por qué no una arista fija

el coste real
Cada salto al supervisor es una llamada al LLM más. Un multiagente es más preciso y más caro: úsalo cuando un agente único ya falle, no antes.

▲ El error que todos cometen: el bucle infinito

El especialista devuelve el control al supervisor, que vuelve a delegar, que vuelve a responder… para siempre. La Regla 1 ("si ya hay respuesta, FIN") es lo único que lo corta. En un supervisor con LLM, esa regla no se delega jamás al modelo: es código. Cuando LangGraph te lance un GraphRecursionError, este es el primer sitio donde mirar.

▸ Para practicar

La garantía que te regala

Con un agente único y 3 tools, no puedes demostrar que una consulta inocente nunca escribirá en el log de auditoría: depende de que el modelo elija bien. Con el patrón supervisor, sí puedes — porque el consultor, literalmente, no tiene esa herramienta.

Eso deja de ser una esperanza y pasa a ser un test. En una financiera, esa diferencia es la que te deja dormir.

Es la misma idea de "divide y acota", pero repartiendo la investigación en vez de repartir por especialidad. LangChain lo ofrece como plantilla (Deep Research with LangGraph): un buen siguiente proyecto cuando domines el supervisor.

Cómo se hablan los servicios

Servicios separados necesitan comunicarse, y hay dos patrones según la urgencia de la respuesta:

Síncrono (REST/HTTP)

"Pregunto y espero la respuesta". Para el camino de consulta: el usuario está esperando. Orquestación llama a ranking, ranking responde.

Asíncrono (colas)

"Dejo el encargo y sigo". Para ingesta: subes 200 PDFs a una cola y los workers los indexan a su ritmo. Nadie espera en línea.

Balanceador de carga

El recepcionista: recibe todas las llamadas y las reparte entre las copias vivas del servicio. Si una copia cae, deja de enviarle tráfico.

La regla del estado: servicios sin memoria propia

Para que un servicio pueda escalar (tener 3, 10, 50 copias) debe ser stateless: ninguna copia guarda nada importante en su propia memoria. ¿Por qué? Si la copia 2 recuerda tu conversación y la siguiente petición cae en la copia 3, la conversación "desaparece". La solución: todo el estado vive afuera — el historial del agente en un checkpointer Postgres/Redis (Módulo 13), los vectores en el vector store, los archivos en un almacén de objetos. Las copias son intercambiables y desechables.

◆ Analogía

Los meseros no llevan libreta propia: toda comanda va al sistema de la cocina. Así cualquier mesero puede atender cualquier mesa, contratar más meseros un sábado es trivial, y si uno se enferma no se pierde ningún pedido.

Kubernetes: le declaras lo que quieres, él lo mantiene

Kubernetes (K8s) orquesta contenedores. Su idea central es declarativa: tú describes en un archivo el estado deseado ("quiero 3 copias del servicio de ranking, con esta memoria") y K8s lo hace realidad y lo defiende: si una copia muere, levanta otra; si un servidor falla, mueve las copias a otro. Dos objetos, dos papeles: el Deployment mantiene vivas las copias; el Service les pone una dirección única y balancea la carga. Con un tercer objeto (HorizontalPodAutoscaler) K8s además escala solo: "si el CPU pasa de 70%, sube de 3 a 10 copias".

Serverless: escalar a cero y pagar por uso

En serverless no administras servidores ni copias: subes una función y la plataforma la ejecuta cuando llega una petición, escalando de 0 a mil instancias sola. El modelo de costos cambia por completo: con K8s pagas por los servidores encendidos (haya o no tráfico); con serverless pagas por ejecución — si nadie pregunta, pagas cero. El precio oculto es el cold start: la primera petición tras un rato de silencio tarda más, porque hay que "despertar" la función.

"Funciona en mi máquina" no basta. En producción necesitas ver qué hace el sistema: cuánto tarda, cuánto cuesta y si está alucinando. Sin instrumentación, vuelas a ciegas — y te enteras de los problemas por los usuarios, que es la peor forma.

◈ Definición · Observabilidad y evaluación

Observabilidad es poder responder qué está pasando ahí dentro sin añadir código nuevo: qué prompt salió, qué herramienta se llamó, cuántos tokens costó, dónde se fue el tiempo. Es sobre el sistema en vivo.

Evaluación es distinto: es medir si las respuestas son buenas, contra un conjunto de casos con respuesta esperada. Es sobre el sistema antes de desplegarlo. Una te dice que el sistema está lento; la otra, que se ha vuelto tonto.

traza (trace)
El árbol completo de una ejecución: cada nodo, cada llamada al LLM, con su entrada, su salida y su duración. En LangSmith se activa con dos variables de entorno.
dataset de evaluación
Pares pregunta → respuesta esperada. Es tu red de seguridad: sin él, "mejoró" es una opinión.
LLM-as-judge
Usar un modelo para puntuar las respuestas de otro cuando no hay una respuesta exacta que comparar. Barato y útil, pero es un juez con sesgos: valídalo contra casos que ya sabes juzgar.
regresión
Que algo que antes funcionaba deje de funcionar. En IA aparece sin tocar tu código: cambia el modelo, cambian tus resultados. Por eso se re-evalúa periódicamente, no solo al programar.

La estructura de un repositorio productivo

📋 Todo esto existe de verdad en el repo: curso_ejemplos/docs/README_runbook.md y curso_ejemplos/docs/adr/ (plantilla + 2 ADRs reales)

El código funcional es solo una parte. Un proyecto empresarial necesita una estructura que facilite colaborar, mantener, desplegar y transferir conocimiento.

◈ Definición · Repositorio productivo

Un repositorio productivo no es uno con más carpetas: es uno del que otra persona puede hacerse cargo sin preguntarte nada. Eso exige tres cosas que el código no dice por sí solo: cómo se opera, por qué está hecho así, y qué avisa si lo rompes.

runbook
El manual de operación. Qué hacer cuando salta un 429, cómo se depura un grafo, cómo se revierte un despliegue. Se escribe antes del incidente, porque durante el incidente nadie escribe nada.
ADR
Architecture Decision Record: una página que registra una decisión y su porqué ("elegimos este vector store porque…"). Su valor no es la decisión, es el contexto — dentro de un año explicará por qué NO se hizo de la forma obvia.
inyección de dependencias
Pasar las piezas caras (modelo, retriever) por parámetro en vez de crearlas al importar el módulo. Es la línea que separa un script de un sistema testeable; el proyecto final lo demuestra.
nada se ejecuta al importar
La regla derivada. Si import config llama a la API, no puedes ni correr los tests ni abrir el módulo en un notebook.
◆ ¿Qué es un ADR?

Un Architecture Decision Record es una nota corta que documenta una decisión importante: qué se decidió, por qué, qué alternativas se descartaron y qué consecuencias trae. Así, quien llegue después entiende el porqué, no solo el qué — y no deshace en marzo una decisión que costó aprender en enero.

La plantilla completa cabe en media página. Este es un ADR real de este mismo curso:

  • Componentes modulares: cada etapa del pipeline en su carpeta, testeable por separado.
  • Scripts de despliegue: K8s + serverless versionados junto al código — el despliegue se lee, se revisa y se repite; no vive en la cabeza de nadie.
  • Adaptadores MCP: integraciones externas aisladas y con los controles de seguridad del Módulo 14.
  • Documentación viva: ADRs + métricas definidas + un runbook de operación.

El README como manual de operación (runbook)

El README de un sistema productivo no describe el código: responde las preguntas de quien lo opera, sobre todo a las 3 de la mañana. Como mínimo:

  • Cómo arrancarlo: comandos exactos, variables de entorno necesarias y dónde conseguirlas.
  • Cómo saber que está sano: qué métricas mirar (Módulo 16) y sus valores normales.
  • Qué hacer cuando falla: los errores conocidos y su primera respuesta ("429 → esperar cuota o activar el fallback"; "respuestas inventadas → revisar qué contexto recuperó la traza").
  • A quién escalar cuando la primera respuesta no alcanza.

Concurrencia

Varios usuarios a la vez, cada uno con su conversación. Ya sabes resolverlo: el thread_id del checkpointer (Módulo 13).

Arranque caro

Indexar el RAG tarda. No puede pasar en cada petición: el agente se construye una vez, al arrancar el servidor.

Errores

Un 429 no puede tumbar el servidor. Se traduce a un HTTP 503 y el servicio sigue vivo para los demás.

La misma idea del Módulo 15b — el lifespan construye el agente al arrancar y lo guarda, porque un servidor stateless puede tener estado de proceso (el índice) mientras el estado de conversación viva afuera, en el checkpointer.

Y lo que sale gratis: FastAPI genera la documentación interactiva en /docs a partir de esos mismos moldes Pydantic, y un GET /salud le dice al balanceador de carga (Módulo 15b) si esta copia sigue viva.

En vez de un archivo gigante, un agente productivo se separa por responsabilidad: state.py (el estado), graph_builder.py (nodos y aristas), rag.py, persistence.py (checkpointer), config.py y — clave en cumplimiento — audit.py, que registra cada decisión y cada tool ejecutada en un log de auditoría (lo viste por dentro en el Módulo 13). Tests y CI: la red que te deja cambiar cosas sin miedo

📋 Existe de verdad: curso_ejemplos/tests/ · proyecto_final/tests/ · .github/workflows/ci.yml — 141 tests, ninguno gasta cuota

Todo el nivel de producción se apoya en una idea silenciosa: puedes cambiar el código porque algo te avisa si lo rompes. Sin eso, cada refactor es una apuesta y cada actualización de librería, una noche larga. Este módulo enseña cómo está tejida esa red — la del propio curso, que puedes correr ahora mismo.

◈ Definición · Test, doble de prueba y CI

Un test es código que ejecuta tu código y falla si el resultado no es el esperado. En IA hay una condición extra: un test no debe llamar al LLM. Si lo hace, es lento, cuesta dinero, y falla por un 429 que no tiene nada que ver contigo — no mide tu código, mide la cuota de Google.

La salida es sustituir el modelo por un doble de prueba: un objeto que se comporta como el modelo pero devuelve respuestas fijas. Así puedes ejercitar el grafo completo, las herramientas y la auditoría sin una sola llamada a la API.

doble / modelo falso
El ModeloFalso del proyecto final: recita un guion de respuestas preparadas. Lo que se testea no es el LLM (no es tuyo), es tu lógica alrededor del LLM.
marcador (-m offline)
Una etiqueta en cada test que permite correr solo los que no gastan cuota. Con --strict-markers, escribir mal el nombre del marcador es un error, no un test silenciosamente ignorado.
CI (integración continua)
Un servidor que corre los tests en cada push, sin que nadie se acuerde de hacerlo. La CI de este curso no tiene la llave de la API — a propósito: si un test empezara a llamar al modelo, fallaría de inmediato.

El problema específico de testear IA

Un test normal es determinista: sumar(2,2) siempre da 4. Pero un LLM devuelve texto distinto cada vez, tarda segundos, cuesta dinero y puede fallar por un 429 que no tiene nada que ver con tu código. Si tus tests llaman a la API, no son tests: son un termómetro de la cuota de Google.

◆ La regla que resuelve casi todo

Separa lo que decide el modelo de lo que decide tu código, y testea lo segundo. La fusión RRF, el troceado, la política de enrutamiento del supervisor, el validador de severidad, el cálculo de coste: nada de eso necesita un LLM. Es tu lógica, es determinista, y es donde de verdad viven tus bugs.

El capstone responde bien. La respuesta a eso no es cambiar de modelo cada semana. Es LLMOps.

◈ Definición · LLMOps

LLMOps es la disciplina de llevar un sistema basado en modelos de lenguaje a producción y mantenerlo ahí: desplegarlo, medirlo, controlar su coste, gobernar lo que entra y lo que sale, y detectar cuándo se degrada.

Se parece a MLOps, pero dos cosas cambian de raíz. Primera: la salida es texto libre y no determinista, así que no hay assert salida == esperada — hay que evaluar, no comprobar. Segunda: el modelo es de otro y se paga por token, así que el coste y la latencia son propiedades de diseño, no detalles de infraestructura.

guardrail
Código determinista que inspecciona lo que entra al modelo o lo que sale de él, y bloquea o sanea. El prompt no es un guardrail: es una petición muy educada.
caché semántico
Caché que compara el significado de las preguntas (similitud coseno entre embeddings), no su texto exacto. Un acierto cuesta $0.
TTFT (time to first token)
Tiempo hasta el primer token de la respuesta. Con streaming, es lo que el usuario percibe como velocidad — no la latencia total.
LLM-as-a-judge
Un modelo que puntúa la respuesta de otro contra una rúbrica explícita. Reproducible y barato; no infalible.
eval gate
El paso del pipeline que corre la evaluación y sale con código 1 si el sistema se degradó. Sin poder de veto, una evaluación es un adorno.

◆ Por qué ese orden y no otro

El guardrail va antes del caché: no queremos ni siquiera vectorizar un intento de inyección, y mucho menos cachearlo. El caché va antes del agente: es lo único que puede evitar la llamada cara. Y el caché guarda después del guardrail de salida — si cachearas la respuesta cruda, el filtro correría una vez y se esquivaría para siempre en cada acierto posterior.

Pilar 1 · Gobernanza: bloquear lo hostil, sanear lo torpe

Es lo más diferenciador frente al MLOps clásico, y lo más fácil de hacer mal. Hay dos riesgos distintos y cada uno pide una respuesta distinta.

▲ Un guardrail por lista negra sube el coste del ataque; no lo hace imposible

Esto es una heurística de subcadenas: barata, determinista y sin cuota. También evadible — un atacante escribe 1gnora tus 1nstrucciones y pasa. En producción se apila encima un modelo guardián. Quien te venda un guardrail impenetrable no ha entendido el problema.

El RBAC: recuperar y autorizar son dos pasos distintos

El RAG recupera por parecido semántico, y eso no sabe nada de permisos. Un fragmento sobre las claves maestras del HSM es perfectamente relevante para «¿cómo se protegen las claves?» — y justo por eso hay que quitárselo a quien no tiene autorización.

◆ El bug que enseñó la lección

La primera versión del clasificador marcaba restricted cualquier texto con las palabras «cifrado» o «personal». Como toda la normativa habla de eso, un analyst —el rol por defecto— no recuperaba ni un fragmento. Un clasificador que lo marca todo como secreto no protege nada: rompe el producto. Hay tests que fijan ese comportamiento para que no vuelva.

Pilar 2 · Coste y UX: el caché que casi filtra datos

Un caché exacto (dict) apenas acierta: «¿hay que cifrar los datos?» y «¿los datos se cifran?» son claves distintas. El caché semántico compara vectores y acierta en las dos. Se vende como una optimización inocente. No lo es.

▲ Los dos peligros del caché semántico

1. Un falso positivo no es lentitud: es una respuesta incorrecta. Con un umbral bajo, «¿debo cifrar los datos?» y «¿debo cifrar los backups?» se parecen mucho, y el usuario recibe con total aplomo la respuesta a una pregunta que no hizo. Un caché mal calibrado no degrada el rendimiento: degrada la verdad. Ante la duda, un fallo caro es infinitamente mejor que un acierto equivocado.

2. El caché es un canal lateral que se salta el RBAC. Si un compliance pregunta por las claves maestras y su respuesta se cachea sin más, el siguiente analyst que pregunte algo parecido recibe material restringido: sin pasar por el retriever, sin pasar por filtrar_por_rol. Toda la gobernanza, esquivada por una optimización de coste. Por eso el rol forma parte de la clave.

Streaming y guardrail de salida: una contradicción real

Para filtrar la respuesta hay que tener la respuesta. Para hacer streaming hay que emitirla antes de tenerla. La mayoría de los tutoriales resuelven esto ignorándolo: hacen streaming y quitan el guardrail.

El precio: la respuesta se ve con 64 caracteres de retraso, unos milisegundos. La fuga baja a cero. Es el intercambio correcto — y hay un test que comprueba el invariante (VENTANA >= longitud_maxima_de_patron()) para que añadir un término largo a la política no rompa el streaming en silencio.

Pilar 3 · Observabilidad: la media esconde al usuario que se va

◆ Por qué p95 y no la media, y por qué TTFT y no latencia

Con 95 requests de 200 ms y 5 de 10 s, la media dice 690 ms y «todo va bien». El p95 dice 10 s, que es lo que sufre 1 de cada 20 usuarios. Las medias esconden precisamente a la gente que se va.

Y con streaming, lo que el ojo mide es el primer token. Un servicio con 4 s de latencia total y 300 ms de TTFT se siente rápido; uno con 2 s y 2 s de TTFT se siente roto. Si solo mides el total, optimizarás lo que nadie nota.

▲ La consecuencia contraintuitiva

Los tokens de salida cuestan varias veces más que los de entrada. Por tanto un RAG que mete 4.000 tokens de contexto no es lo caro: lo caro es una respuesta larga. Optimizar el prompt para ahorrar suele ser optimizar el sitio equivocado.

El tracing (Langfuse, self-hosted) degrada a no-op: sin llaves, observar() devuelve la función intacta y callbacks() devuelve []. Un observador que tumba lo observado no es observabilidad, es un fallo con dashboard. El precio de esa decisión está escrito en su ADR: si el tracing se rompe, nadie recibe una alerta.

Pilar 4 · Evaluación: la tríada RAG y el poder de veto

«El RAG responde mal» no es un diagnóstico: es una queja. La tríada la convierte en diagnóstico, porque separa tres fallos distintos que producen el mismo síntoma.

MétricaPregunta que respondeSi está baja…Lo que NO arregla nada
faithfulness¿La respuesta se sostiene solo en el contexto?El modelo alucina → arregla el promptCambiar el retriever
answer relevance¿Responde a la pregunta que se hizo?El modelo divaga → arregla el promptCambiar el vector store
context precision¿Los fragmentos recuperados eran los correctos?Falla el retriever → chunking, k, híbridaCambiar de LLM: le das los párrafos equivocados

Cada métrica mira solo dos de los tres vértices (pregunta ↔ contexto ↔ respuesta). Que cada una ignore uno es lo que las hace independientes: si las tres vieran los tres, medirían lo mismo tres veces.

▲ Sin la segunda puerta, esto no sirve de nada

Con 20 ejemplos a 0.95 y uno a 0.0 —el agente alucina la multa de la Regla 1, o le revela las claves maestras a un analyst— la media sale 0.90 y el deploy pasa tan tranquilo. La media es exactamente la estadística que oculta el fallo que más importa. Hay un test que reproduce ese escenario.

Y la regla de oro cuando el gate te bloquea: no subas el umbral para que pase. Es un contrato, no un obstáculo. Si lo bajas para desplegar hoy, mañana no protege de nada.

Los prompts son código

Un prompt hardcodeado en una f-string es un prompt que nadie revisa en el PR, que no tiene versión, y que cuando falla no se puede correlacionar con nada. Aquí vive en prompts/agente_gobdata.yaml, con version: y un changelog que explica por qué cambió cada versión.

Cómo se prueba todo esto sin gastar un token

La misma regla del capstone, llevada al extremo: todo lo caro entra por parámetro. La API completa se levanta con un agente falso que recita tokens, un caché con embeddings deterministas y ningún servicio en pie.

Ese «nunca llega al agente» es la parte que importa: es lo que ahorra dinero y lo que evita el riesgo. Y solo se puede afirmar contando las invocaciones del doble.

◆ Los dos workflows de CI, y por qué son dos

ci.yml corre en cada push: 338 tests offline, gratis, nunca llama a la API. eval-gate.yml corre a mano o antes de una release: sí gasta cuota y sí puede vetar el deploy. Confundirlos es el error clásico — o pagas una evaluación completa por cada commit de un README, o no evalúas nunca porque «la CI ya pasa».

Sin el ToolMessage + la reinvocación, el modelo nunca ve el resultado. El error clásico (Módulo 08).

Retry reintenta lo idéntico; para un prompt malo no hay reintento que valga. El fallback va a otro modelo, no a otro prompt (Módulo 09).
